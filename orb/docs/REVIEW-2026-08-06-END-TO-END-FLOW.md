# ADHD Focus Orb — End-to-End Flow Problem Inventory

**Review date:** 2026-08-06  
**Scope:** mobile launch → mic capture → VAD → WebSocket relay → STT → session/runtime → atomizer → TTS → audio playback, plus failure handling, cost, identity, and verification.  
**Verdict:** the implemented path does not currently satisfy the blueprint's live voice contract. The problems below are ordered by where they break the user journey.

## 1. The app can appear to work without the microphone or backend

**Severity: P0**  
**Failure → cause → effect:** app start immediately injects the final transcript `Open the first small action` into `VoiceLoopController`; `AppController.start()` does this before any user speech, and `App.tsx` constructs the runtime with the same hardcoded task. The app can therefore produce a greeting/first-step response while no mic frame, STT transcript, or backend response has completed. This masks a broken voice path and explains why the Android evidence only shows the default phrase.  
**Evidence:** `apps/mobile/src/AppController.ts:27-45`, `apps/mobile/src/App.tsx:96-110, 188-200`, `docs/evidence/android-e2e/focus-orb-android-logcat.txt:1-8`.  
**Blueprint mismatch:** `03-VOICE-LATENCY-PIPELINE.md` requires the user audio stream to drive the turn; the current launch path bypasses it.

## 2. Mic permission and local mic activity are falsely presented as end-to-end listening

**Severity: P0**  
**Failure → cause → effect:** the UI changes to `Listening` when the first native `OrbMicFrame` arrives, not when the relay receives it or STT acknowledges it. `sendAudio()` has no receipt, sequence, or failure result; the relay intentionally emits no client-visible ack for ordinary mic frames. The user can see mic access and `Listening` while frames are queued, dropped, sent to the wrong host, or rejected by the backend.  
**Evidence:** `apps/mobile/src/App.tsx:118-124, 265-272, 344-356`, `apps/mobile/src/runtime/VoiceLoopController.ts:121-125`, `apps/mobile/src/voice/RelayClient.ts:104-108`, `backend/relay-rs/src/main.rs:200-205`.

## 3. WebSocket connection failures are swallowed and cannot produce a user-visible failure

**Severity: P0**  
**Failure → cause → effect:** `RelaySocket` discards `onerror`, queues frames indefinitely while connecting, has no open timeout, and does not reject or clear queued frames after close. `RelayClient` only flips `closed` on close; the app has no reconnect, connection state, timeout, or transport error callback. TTS sent while the socket is still connecting is treated as deliverable and can remain queued forever; mic frames can be silently lost.  
**Evidence:** `apps/mobile/src/voice/RelaySocket.ts:29-59`, `apps/mobile/src/voice/RelayClient.ts:45-62, 104-108`, `apps/mobile/src/App.tsx:221-231`.

## 4. Provider failure closes the voice loop without the required presence-preserving response

**Severity: P0**  
**Failure → cause → effect:** Rust converts any provider error into `closing(provider_failure)`. The mobile handler only stops capture; it does not emit a cached failure announcement, keep/recover the presence bed, expose a response envelope, or reconnect. `relay.speak()` also does not use native fallback once a relay client exists, even if that client is unhealthy. A dead STT/TTS sidecar therefore becomes silence/no response.  
**Evidence:** `backend/relay-rs/src/session.rs:228-246`, `apps/mobile/src/App.tsx:153-163, 247-250`, `blueprints/ADHD-Focus-Orb-L8-Deep-Dive/09-FAILURE-DR-AND-DEGRADATION.md`.

## 5. The mobile relay URL is not reliably injected into the React Native bundle

**Severity: P1**  
**Failure → cause → effect:** `App.tsx` reads `process.env.ORB_RELAY_HTTP_URL` and `process.env.ORB_RELAY_WS_URL`, but the project Babel and Metro configuration has no environment-variable transform or bundle-time injection. The app therefore falls back to hardcoded `localhost`/`10.0.2.2` URLs unless the runtime happens to provide those variables. A deployed device has no reliable route to the relay.  
**Evidence:** `apps/mobile/src/App.tsx:59-67`, `babel.config.js:1-7`, `metro.config.js:1-45`.

## 6. The STT implementation is batch-at-end, not streaming

**Severity: P0**  
**Failure → cause → effect:** Sarvam and Deepgram `pushAudio()` only append bytes to an in-memory buffer and always return no transcript; the provider request happens only after `end_of_turn`. The only partial transcripts are generated by the fake provider. Semantic endpointing receives `pauseMs = 0` and can only act on a final transcript. The user gets no real partials, no early semantic endpoint, and no response until local VAD has already ended the turn.  
**Evidence:** `backend/voice-provider-sidecar/src/stt/sarvam.ts:18-30`, `backend/voice-provider-sidecar/src/stt/deepgram.ts:13-34`, `apps/mobile/src/App.tsx:224-231`, `apps/mobile/src/runtime/VoiceLoopController.ts:154-165, 179-184`.  
**Blueprint mismatch:** `03-VOICE-LATENCY-PIPELINE.md` requires streaming partials and a streamed voice path.

## 7. The relay blocks its async socket loop on synchronous provider I/O

**Severity: P0**  
**Failure → cause → effect:** the HTTP provider adapter uses blocking `TcpStream::connect`, `write_all`, and `read_to_string` inside the Rust session handler, with no connect/read/write timeout. One slow or stalled sidecar call blocks processing of that connection; a slow final STT/TTS request prevents timely control frames and can make the user wait indefinitely.  
**Evidence:** `backend/relay-rs/src/provider.rs:162-188, 198-245`, `backend/relay-rs/src/main.rs:178-183`.

## 8. TTS is buffered end-to-end even though the protocol looks chunked

**Severity: P1**  
**Failure → cause → effect:** the sidecar waits for the provider's complete audio response, then chunks the completed byte array; Rust waits for `tts.synthesize()` before sending `speech_starting` and audio. The first audio chunk cannot arrive while synthesis is still running. This is not streamed TTS and cannot meet the blueprint's first-audio or zero-think-time targets.  
**Evidence:** `backend/voice-provider-sidecar/src/index.ts:88-108`, `backend/relay-rs/src/session.rs:156-183`, `backend/relay-rs/src/main.rs:229-243`.

## 9. Barge-in is not cancellable on the real provider path

**Severity: P1**  
**Failure → cause → effect:** Rust handles `speak` synchronously and only processes the next WebSocket frame after synthesis returns. A `barge_in` frame cannot interrupt an in-flight provider call; it only changes state after the TTS request has already completed. The 100 ms yield constant is explicitly not wired into the socket path.  
**Evidence:** `backend/relay-rs/src/session.rs:156-202`, `backend/relay-rs/src/main.rs:166-183`, `backend/relay-rs/src/latency_budget.rs:13-23`.

## 10. The app has no actual audio format validation on either side of the wire

**Severity: P0**  
**Failure → cause → effect:** the client interprets every binary TTS message as mono PCM16 at 16 kHz; the sidecar strips a WAV `data` chunk but does not validate or convert its sample rate, channel count, encoding, or bit depth. A non-WAV response is sent through unchanged after a warning. Fish's provider code itself records that intelligibility has not been manually verified. Any MP3/compressed response, stereo response, different sample rate, malformed PCM, or odd-byte frame is played as raw 16 kHz mono samples, producing clicks, noise, wrong speed, or unintelligible speech.  
**Evidence:** `apps/mobile/src/voice/RelayAudioPlayer.ts:29-57, 88-100`, `backend/voice-provider-sidecar/src/wav.ts:53-88`, `backend/voice-provider-sidecar/src/index.ts:90-106`, `backend/voice-provider-sidecar/src/tts/fish.ts:53-64`.

## 11. The fake provider emits non-speech bytes that the client plays as voice

**Severity: P0**  
**Failure → cause → effect:** Rust's fake TTS returns 320 zero bytes followed by 320 one bytes; the sidecar fake returns the same pattern. The client treats these bytes as PCM and schedules them as audible TTS. Rust defaults `ORB_RELAY_PROVIDER` to `fake`, and the sidecar defaults both STT and TTS to `fake` when its environment is absent. This directly produces an unrecognisable/noise voice while all protocol lifecycle frames still look successful.  
**Evidence:** `backend/relay-rs/src/provider.rs:74-86, 345-360`, `backend/voice-provider-sidecar/src/index.ts:14-22, 104-106`, `backend/voice-provider-sidecar/src/tts/fake.ts:3-11`.

## 12. The native speech fallback is also not the configured Orb voice

**Severity: P1**  
**Failure → cause → effect:** when the relay is absent or closed, the fallback ignores `voiceId` and `emotion` and delegates to platform TTS using the device's default locale/voice. This creates a different, device-dependent voice and can be robotic or unintelligible; it also contradicts the blueprint's explicit cloud-only voice-quality decision.  
**Evidence:** `apps/mobile/src/voice/SpeechPort.ts:20-35`; the fallback selection is `apps/mobile/src/App.tsx:153-163`.

## 13. The voice capture format is assumed, not proven at the mobile boundary

**Severity: P1**  
**Failure → cause → effect:** the JS layer decodes base64 without validating the payload, declared byte length, even PCM sample alignment, or timestamp monotonicity. Android silently skips all `AudioRecord.read()` results `<= 0` and continues without emitting a capture error. There is no frame-drop/backpressure metric across the native-to-JS `DeviceEventEmitter` bridge. Mic permission can be granted and a frame can be observed while the actual stream is malformed or incomplete.  
**Evidence:** `apps/mobile/src/voice/NativeMicPort.ts:51-66, 135-149`, `android/app/src/main/java/com/orbmobile/OrbMicModule.kt:96-123`.

## 14. VAD is loudness detection, not speech detection, and there is no visible AEC path

**Severity: P1**  
**Failure → cause → effect:** VAD maps RMS energy directly to speech probability and explicitly treats every sufficiently loud non-speech sound as speech. The capture path has no verified acoustic echo-cancellation boundary, so the orb's own TTS, fan noise, taps, or room noise can trigger false turns and end-of-turn calls. This creates extra STT calls, missing turns, and possible self-interruption.  
**Evidence:** `apps/mobile/src/voice/NativeMicPort.ts:24-41`, `android/app/src/main/java/com/orbmobile/OrbMicModule.kt:55-58`; the blueprint requires full-duplex/AEC behavior in `03-VOICE-LATENCY-PIPELINE.md`.

## 15. Transcript identity and turn ordering are not preserved through the client

**Severity: P1**  
**Failure → cause → effect:** the server sends `tenant_id` and `session_id` on transcript frames, but `RelayClient` discards them and forwards only `(text, is_final)`. The controller has no turn sequence, server request ID, or stale-response guard. A delayed final transcript can be applied to a later turn/session state.  
**Evidence:** `apps/mobile/src/voice/RelayClient.ts:126-145`, `apps/mobile/src/App.tsx:224-231`, `apps/mobile/src/runtime/VoiceLoopController.ts:179-184`.

## 16. Realtime voice identity is incomplete and unauthenticated

**Severity: P1**  
**Failure → cause → effect:** the mobile voice protocol carries only hardcoded `tenant_id = t0` and `session_id = local-session`; it does not carry `user_id`, an auth token, or a server-issued session identity. Rust validates that later frames match the first arbitrary tenant/session pair, but does not authenticate ownership. The sidecar receives only `session_id` for STT and no tenant/user identity for TTS. Any caller that reaches the relay can claim arbitrary identity values, and voice usage cannot be reliably attributed to a user or tenant.  
**Evidence:** `apps/mobile/src/App.tsx:96-103, 128-131`, `apps/mobile/src/voice/RelayClient.ts:64-90`, `backend/relay-rs/src/session.rs:32-43, 120-135`, `backend/relay-rs/src/provider.rs:198-245`, `backend/voice-provider-sidecar/src/index.ts:53-90`.

## 17. The backend is materially hardcoded to a T0/demo session

**Severity: P1**  
**Failure → cause → effect:** tenant, user, session, starter task, starter step, greetings, crisis response, provider, voice ID, model version, prompt version, bed color, gain, and logical policy clock are source-level defaults. The response envelope reports `t0-deterministic` and `t0.focus-session.v2` even when the request came through the relay. The live path is therefore not a real user/session flow and several response fields are declarations rather than observed backend facts.  
**Evidence:** `apps/mobile/src/App.tsx:96-112, 128-131`, `apps/mobile/src/runtime/T0FocusSession.ts:88-104, 298-312, 460-503`, `backend/relay-rs/src/provider.rs:74-109`.

## 18. Context warmup and cache priming are disconnected from the mobile flow

**Severity: P1**  
**Failure → cause → effect:** the mobile app never calls `/v1/session/warmup` or `/v1/cache/prime`, so `context_pack` is absent and the session starts with empty recent tasks/open loops. The cache endpoint is a deterministic no-op. The runtime's fallback embedding is `[1]` for every non-empty task, so if a context pack is supplied later, unrelated non-empty tasks have identical query vectors and can be treated as reusable.  
**Evidence:** no mobile call site exists for those routes; `apps/mobile/src/runtime/T0FocusSession.ts:126-144, 414-416`, `backend/relay-py/src/orb_relay/app.py:240-272`.

## 19. Atomizer failures degrade silently and report false provenance

**Severity: P1**  
**Failure → cause → effect:** any non-402 atomizer HTTP failure, timeout, malformed JSON, or invalid output falls back to the static “Open the first small action” step. The static result is labeled `cache_hit`, and any unknown relay source—including `fallback`—is also mapped to `cache_hit`. The user and envelope cannot distinguish a real cached result, a model result, a backend failure, and a local hardcoded fallback.  
**Evidence:** `apps/mobile/src/runtime/AtomizerPort.ts:77-139, 175-179`, `apps/mobile/src/App.tsx:104-110`.

## 20. Voice usage is not connected to the cost reservation/control plane

**Severity: P1**  
**Failure → cause → effect:** Python meters the atomizer request, but Rust only increments in-process `stt_frames` and `tts_chars` counters and prints them when the session ends. The code explicitly says the out-of-band reporter is not wired. No voice reservation is made before STT/TTS, no usage event reaches the Python meter, and a user can consume provider voice spend without the ₹4/session guard seeing it.  
**Evidence:** `backend/relay-py/src/orb_relay/app.py:149-237`, `backend/relay-rs/src/session.rs:38-43`, `backend/relay-rs/src/main.rs:253-267`, `backend/relay-py/src/orb_relay/cost/meter.py:120-205`.

## 21. The declared latency/eval metrics are not live voice measurements

**Severity: P1**  
**Failure → cause → effect:** `/v1/eval/metrics` aggregates local deterministic corpus/replay data and rejects caller observations. The consistency harness uses scripted gateway responses with default `K=5` over a small fixture set, not the blueprint's `K=10 × N=200`. The voice replay counts are expanded synthetic records, not 200 recorded audio-in/audio-out sessions. Green unit/eval results therefore do not prove mic → STT → runtime → TTS latency, intelligibility, silence gaps, or barge-in behavior.  
**Evidence:** `backend/relay-py/src/orb_relay/app.py:286-300`, `backend/relay-py/src/orb_relay/eval/consistency_replay.py` module documentation and `DEFAULT_CONSISTENCY_K`, `backend/relay-py/src/orb_relay/eval/gates.py:39-75, 220-260`.

## 22. The realtime smoke test cannot establish which relay it tested

**Severity: P1**  
**Failure → cause → effect:** `smoke-realtime.mjs` hardcodes port `8091`, starts another relay on the same port, does not verify child ownership or bind success, and continues until it connects to whichever process is already listening. The observed run failed with `Error: expected transcript frame`; an existing `orb-relay-rs` process was already listening on `127.0.0.1:8091`. The test result is therefore neither a valid pass nor a clean diagnosis of the current deployment.  
**Evidence:** `scripts/smoke-realtime.mjs:4-19, 90-101`, `scripts/dev.sh:19-23, 57-80`.

## 23. Current Android evidence proves only boot-time native speech, not the voice journey

**Severity: P0**  
**Failure → cause → effect:** the recorded log contains presence startup and `focus-orb:speak Open the first small action`; it contains no native mic frame count, WebSocket open/send, relay receipt, STT partial/final, atomizer response, TTS provider label, audio format, or audible-quality assertion. The audio-budget file reports only local presence/speech-request timing. The evidence cannot distinguish “mic never sent,” “relay unreachable,” “STT never finalized,” “provider failed,” and “TTS bytes were noise.”

## 24. The HTTP surfaces have no visible authentication, rate limiting, or payload backpressure

**Severity: P1**  
**Failure → cause → effect:** relay, provider sidecar, and atomizer routes accept tenant/session fields as request data but have no auth dependency, rate limiter, request-size limit, audio-duration limit, or concurrency budget. The sidecar reads arbitrary JSON bodies and converts arbitrary `audio_bytes` arrays; a client/retry storm can grow memory and provider spend, and the local relay can be driven by an untrusted caller.  
**Evidence:** `backend/relay-py/src/orb_relay/app.py:27-39, 144-153`, `backend/voice-provider-sidecar/src/index.ts:32-37, 52-120`, `backend/relay-rs/src/main.rs:114-154`.

## 25. Sensitive provider credentials are present as plaintext in the local worktree

**Severity: P0 security**  
**Failure → cause → effect:** the untracked `.env` contains provider API credentials in plaintext. The file is not a safe deployment secret boundary, and the current working tree is heavily dirty/untracked, increasing the chance of accidental inclusion in an archive, screen capture, log, or client handoff.  
**Evidence:** `.env:1-15` (credential values intentionally omitted from this report); `.gitignore` and the working-tree state do not make the values safe once copied or exposed.

## 26. Sensitive voice/session data has no demonstrated retention or deletion boundary

**Severity: P2**  
**Failure → cause → effect:** the system processes raw voice, transcripts, task content, and health-adjacent cognitive evidence, while the context store persists completed atomizations in SQLite. The reviewed flow has no user deletion route, retention expiry, provider deletion contract, or documented data lifecycle. This is an operational/privacy gap for any real user session.  
**Evidence:** `backend/relay-py/src/orb_relay/app.py:35-39, 218-227`, `backend/relay-py/src/orb_relay/store/context_store.py`, and the absence of a deletion/retention boundary in the reviewed mobile/backend flow.

## 27. The first spoken line is a native hardcoded demo, not the Orb session greeting

**Severity: P0**  
**Failure → cause → effect:** Android speaks `Open the first small action` from `OrbGreeting` during `MainActivity.onCreate()`, before React Native, authenticated user data, backend warmup, or the JS runtime exist. The JS runtime's greeting envelope is only stored in state by `AppController`; it is not sent to `relay.speak()`. The requested `Good morning, Rachit` behavior is therefore impossible in the current path, and the first audible phrase is not controlled by the backend or the configured Orb voice.  
**Evidence:** `android/app/src/main/java/com/orbmobile/OrbGreeting.kt:10-57`, `android/app/src/main/java/com/orbmobile/MainActivity.kt:12-16`, `apps/mobile/src/AppController.ts:21-44`, `apps/mobile/src/runtime/T0FocusSession.ts:67-72, 255-260`.

## 28. User data is not loaded before the session starts and no fast-retrieval warmup is issued

The first greeting cannot use the user's real name, and retrieval starts with an empty context pack. There is no parallel warmup/preload boundary that makes the backend ready while the cached greeting plays.

## 35. The mumbled voice has three independent confirmed failure paths

**Severity: P0**  
**Failure → cause → effect:** the heard audio can be (a) native Android TTS using `Locale.getDefault()` rather than `orb.warm.v1`, (b) Rust/sidecar fake bytes consisting of zeros and ones played as PCM, or (c) real provider bytes with an unverified codec/sample-rate/channel contract played as fixed 16 kHz mono PCM. The current logs show the real Fish sidecar was unavailable, so the heard voice was not proven to be valid Fish output. The system has no audio header/format/intelligibility check to identify which path played.
**Evidence:** `android/app/src/main/java/com/orbmobile/OrbGreeting.kt:47-50`; `backend/relay-rs/src/provider.rs:345-360`; `backend/voice-provider-sidecar/src/tts/fake.ts:3-11`; `apps/mobile/src/voice/RelayAudioPlayer.ts:29-57`; `/tmp/orb-dev-logs/relay-rs.log:5-6`.

## 36. Gateway observability is not correlated with the user turn

The log contains full task/response text, yet cannot be joined to a device launch or voice turn. ## 37. The backend has no explicit readiness dependency graph

**Severity: P1**

## 38. Startup greeting, warmup, and realtime socket have no ordered launch protocol

**Severity: P1**  
**Failure → cause → effect:** Android native greeting, React presence boot, WebSocket construction, mic permission, synthetic task injection, and backend atomization race independently. This makes the first phrase, user data, socket state, and first backend request nondeterministic across cold starts.
**Evidence:** `android/app/src/main/java/com/orbmobile/MainActivity.kt:12-16`; `apps/mobile/src/App.tsx:211-295`; `apps/mobile/src/AppController.ts:21-44`.

## 39. The current provider/API failures are not surfaced as spoken, user-safe messages

**Severity: P0**  
**Failure → cause → effect:** provider failures become a closing frame or a swallowed fetch/socket error. # Suggested fixes

These are the implementation fixes mapped one-to-one to the problems above. The minimum P0 slice below has now been applied and verified; the remaining items are still follow-up work.

## Fix 1 — Remove the synthetic startup turn

Delete the automatic final transcript injection from `AppController.start()`. Startup should only initialize the runtime, boot the cached greeting, open the listening lifecycle, and wait for a real VAD/STT turn. Keep `Open the first small action` only as a test fixture or explicit T0 demo profile, never as the production task.

**Acceptance:** a fresh launch produces only the cached greeting; no atomizer call, `acceptAudio()`, or `speakCurrentStep()` occurs until a real final transcript arrives.

## Fix 2 — Add end-to-end audio receipt accounting

Add monotonically increasing `frame_id`, `turn_id`, and byte counts to the audio stream. The relay should periodically acknowledge the highest received frame and report `frames_received`, `bytes_received`, and `last_frame_id`. The mobile UI must distinguish `mic capturing`, `relay connected`, and `backend receiving`.

**Acceptance:** a device log can prove native capture → WebSocket send → relay receipt for one turn, and a missing receipt changes the UI to an actionable transport error.

## Fix 3 — Replace the socket wrapper with an explicit connection state machine

Model `connecting`, `open`, `closing`, `closed`, and `failed` states. Add an open timeout, bounded pre-open queue, send failure propagation, close/error callbacks, reconnect with capped exponential backoff, and a per-turn deadline. Never treat a connecting socket as healthy for TTS delivery.

**Acceptance:** DNS failure, refused connection, mid-turn close, and a socket that never opens each produce a bounded failure event instead of an invisible queue.

## Fix 4 — Implement the provider-failure degradation contract

On STT/TTS failure, keep the presence bed alive, stop the voice socket, set an explicit `voice_unavailable` state, and play a pre-synthesized premium cached phrase such as “I can’t hear you right now, but I’m still here.” Do not route novel text through platform TTS. Preserve the last valid response envelope and allow a controlled reconnect.

**Acceptance:** killing the sidecar during capture or synthesis produces one cached failure announcement, zero bare-silence gaps beyond the budget, and a visible/recoverable state.

## Fix 5 — Make relay endpoint configuration a real build/runtime contract

Use a dedicated React Native runtime configuration module populated by Metro build variables or native build configuration. Validate `ws`/`wss` and `http`/`https` endpoints at boot, print the resolved host without secrets, and fail closed when a release build still points at loopback.

**Acceptance:** dev Android, dev iOS, staging device, and release builds each show the intended relay endpoint in startup diagnostics.

## Fix 6 — Replace batch STT with a true streaming adapter

Give the sidecar a provider-neutral streaming interface with `open`, `push`, `partial`, `final`, `error`, and `close`. Use provider WebSocket/streaming APIs where available; keep audio frames flowing until the relay endpoint decision, then finalize once. Preserve provider partial confidence and timestamps.

**Acceptance:** real provider partial transcripts arrive before VAD end-of-turn, semantic endpointing consumes them, and a recorded turn meets the blueprint's partial and final latency budgets.

## Fix 7 — Remove blocking provider I/O from the Rust socket task

Use an async HTTP/WebSocket client with connect, write, read, and total request deadlines. Run each provider operation under a cancellation-aware task; cap concurrent provider calls per session and tenant. A temporary `spawn_blocking` bridge is acceptable only as an interim guard, not the final streaming design.

**Acceptance:** a stalled provider cannot block control-frame handling or another session, and timeout telemetry identifies connect, provider, and relay portions separately.

## Fix 8 — Stream TTS from provider to device

Change the TTS contract from `synthesize() -> complete byte array` to an async chunk stream. Emit `speech_starting` as soon as synthesis is admitted, forward validated chunks as they arrive, and emit `speech_complete` only after the final chunk. Select a provider/API that actually supports first-audio streaming for the production voice.

**Acceptance:** first audio is timestamped independently from full synthesis completion and the voice-to-voice harness measures the first-chunk target, not total request completion.

## Fix 9 — Make barge-in cancel the active synthesis task

Store the active TTS task and cancellation token in the relay session. `barge_in` must cancel provider generation, stop the playback node immediately, restore the bed, and return the session to listening without waiting for provider completion. Drop late chunks from the cancelled generation using a generation ID.

**Acceptance:** an injected user voice onset stops audible TTS within 100 ms in a real-device test, with no late audio from the cancelled turn.

## Fix 10 — Enforce one explicit media format at every boundary

Choose and document the production transport format. For the current PCM design, validate PCM16 little-endian, mono, sample rate, byte alignment, and duration at ingress; validate WAV `fmt` metadata before stripping; reject compressed/non-WAV output instead of forwarding it; resample explicitly when needed. Include format metadata in the TTS contract and fail closed on mismatch.

**Acceptance:** malformed, stereo, non-16 kHz, odd-byte, MP3, and truncated payload fixtures are rejected with typed errors; valid provider audio is listened to and recorded as evidence.

## Fix 11 — Isolate fake providers from production behavior

Make fake STT/TTS selectable only through an explicit test profile. Production startup must fail if the relay or sidecar resolves to `fake`; health output must expose provider labels. Replace fake TTS byte patterns with a test-only generated tone or a fixture that tests framing without being presented as speech.

**Acceptance:** a release boot with missing provider configuration fails loudly, while the realtime smoke test explicitly asserts `fake` and never doubles as voice-quality evidence.

## Fix 12 — Remove platform TTS from the voice-quality path

Delete the native synthesizer as a substitute for the configured Orb voice. When cloud TTS is unavailable, speak only cached premium phrases and expose “novel speech unavailable.” Keep native TTS, if retained at all, behind a developer-only diagnostic flag.

**Acceptance:** no production response invokes `OrbSpeech`; all audible production phrases are either cached verified assets or validated cloud audio from the configured provider voice.

## Fix 13 — Validate and observe native capture frames

Validate base64 decoding, byte length, PCM alignment, timestamps, and frame duration before passing audio to VAD. Emit native read errors and terminal capture events instead of silently looping on non-positive reads. Add counters for captured, decoded, queued, sent, acknowledged, dropped, and rejected frames; cap the JS bridge queue.

**Acceptance:** a simulated read failure, malformed base64, short frame, and JS backpressure event each reaches the UI/dev telemetry as a distinct error.

## Fix 14 — Use real VAD plus acoustic echo cancellation

Put AEC/noise suppression in the capture graph and feed the playback reference into it. Replace RMS-only VAD with a speech detector calibrated for the supported devices/languages, retaining the pure gate as the state machine. Add noise, fan, music, and self-TTS fixtures.

**Acceptance:** self-played Orb speech does not create a user turn, loud non-speech does not create repeated STT calls, and the VAD suite reports false-start/false-end rates by device condition.

## Fix 15 — Preserve and validate turn identity end-to-end

Add `turn_id` and `generation_id` to client frames, provider requests, server frames, and response envelopes. The mobile client must validate tenant/session/turn identity before dispatching a transcript and discard stale generations. Add a timeout for a final transcript that never arrives.

**Acceptance:** delayed transcript, duplicate transcript, wrong session, and late cancelled-TTS frames are ignored and logged with their IDs.

## Fix 16 — Introduce authenticated session bootstrap and tenant propagation

Replace hardcoded identity with an authenticated session bootstrap that returns server-issued `tenant_id`, `user_id`, `session_id`, and authorization context. Enforce ownership at the relay, pass user/tenant identity to the sidecar and cost plane, and avoid trusting client-supplied tenant IDs as authorization.

**Acceptance:** an unauthenticated caller is rejected; cross-tenant and cross-user frame injection is rejected; every provider and cost event contains the authorized identity.

## Fix 17 — Separate production composition from the T0 demo profile

Move starter task, greeting, voice, provider, model, prompt, bed, and policy settings into versioned configuration. Construct the production runtime from the authenticated session and server response; keep deterministic T0 defaults behind an explicit `T0_DEMO=true` profile. Populate envelope metadata from actual selected provider/model/source.

**Acceptance:** two users receive distinct session IDs and tasks, and a production envelope never claims `t0-deterministic` or a fake provider unless the explicit demo profile is enabled.

## Fix 18 — Wire warmup, context reuse, and cache priming into session startup

Call `/v1/session/warmup` after authenticated session creation and pass the returned context pack into the runtime. Replace the one-bit embedding with a real server-owned embedding/retrieval contract or disable vector reuse until one exists. Make `/v1/cache/prime` prime a real provider cache or report `not_supported`, never `primed=true` for a no-op.

**Acceptance:** a repeated task can prove a real context reuse hit, an unrelated task cannot reuse it, and cache metadata identifies whether audio/model cache was actually primed.

## Fix 19 — Make atomizer fallback explicit and truthful

Separate `model`, `cache_hit`, `reuse`, `fallback`, `timeout`, and `provider_error` in the response schema. Do not map unknown/fallback sources to `cache_hit`. Return a user-safe degraded envelope with a visible telemetry status, and use bounded retry/failover rules rather than catching every error into the static starter step.
