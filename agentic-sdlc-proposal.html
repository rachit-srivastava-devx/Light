SCOPE

What we are building, and the order we build it in

Two things we measured decide the order and the scope. We state them here because every phase and every day estimate in this document comes from them.

Limit 1 — how fast we can review sets how fast we ship, not how fast we can write code

A reviewer can get through about 4 pull requests an hour. That number stays the same no matter who or what wrote the code. If code gets written faster than it gets reviewed, the queue just gets longer. It does not mean more code gets merged. The project's own design document calls this blind spot 04: "a multi-day run piles a PR queue against your ~4/hr review ceiling."

So the plan builds the review-side tools first. Those are the gate, the knowledge base, and the spoken PR walkthrough. A gate is an automatic check that blocks a bad change before a person sees it. These come before any tool that writes code on its own. It also adds a limiter (task 4.3). This pauses work when the queue hits a set limit.

Limit 2 — much of what we planned to build already exists as a product

Claude Code, which we already pay for, comes with subagents, hooks, skills, MCP mounting, and cloud agents that turn a spec into a PR. Semgrep, Greptile and DX already sell the gate, the PR reviewer, and the DORA dashboard, for $12–48 per developer a month. Section 09 checks each part of our plan against what is already for sale.

So we scope it this way: build the two things nobody sells, and buy or reuse the rest. That gives a 118-day programme. 18 of those days are the testing setup in section 20.

The two problems this fixes for each developer

Everything below works toward exactly two goals. Both are measured per developer. Orb is how each one reaches the developer.

Problem 1 · The knowledge and learning gap

No one developer can remember everything the team decided, broke, or promised a client. So the same mistake happens again. The same question goes to the same senior engineer again. Every task starts from zero.

Measured: 42% of a developer's week goes to fixing old problems and redoing work (Stripe). AI makes this worse, not better — copy-pasted code blocks rose 8× and rewrites doubled, because a model cannot see what already exists (GitClear, 211M lines).

Fixed by: the knowledge base writes down a lesson every time code merges. Orb answers "why is it like this" out loud, reading from that record instead of a colleague's memory. We measure this with the repeat-mistake rate, section 05.

Problem 2 · Reviews cap out at about 4 pull requests an hour

A reviewer gets through about four pull requests an hour, and that does not change when a machine writes the code. Any time spent making code generation faster, without also speeding up review, just makes the queue longer.

Measured: a pull request takes 24 to 48 hours to merge, on average. 7 to 12 of those hours are just waiting for the first review (LinearB, 6.1M pull requests).

Fixed by: the gate removes the findings a machine can spot, before a human ever looks. Orb then walks the developer through the change — what it does, why, and the two spots worth a closer look — so review starts with context instead of from scratch. We measure this with review minutes per PR, section 05.

How our design responds to these two problems

We can fix both problems. Neither gets fixed by just using a smarter model.

The gate controls change size — it automatically rejects changes that are too big, untested, or unsafe, before a human sees them. The knowledge base fixes missing context — it looks up what the team already decided, already broke, or already promised a client. Recent research on this finds the same thing: what matters is the quality of what gets looked up, not just whether something gets looked up at all.

Using AI without these two controls gets you the same bad result METR measured. That is why we build the gate and the knowledge base before we build tools that generate more code. Section 07's metrics measure both of these directly.

The three worst problems, rated frustration 5, in detail

Same symptom, three different root causes

Duplicate Shopify orders that double-counted inventory happened three separate times over two months, each for a different reason — an employee tapping twice, a flaky network hiding a success message, and a timing bug with a multi-minute window. Three separate root-cause investigations, about 30 hours total.

Each time it happened, it looked the same to the client, so it cost trust each time. The knowledge base's rule_id tells the symptom apart from the cause. This is exactly what the team asked for: "root-cause tag on every bug so symptom-versus-cause recurrence is visible."

44 days, request to done

One cancellation feature took 9 pull requests, 3 repositories, and 6 branches. 5 commit messages showed up two or three times each, because changes were cherry-picked instead of promoted properly. A finished gift-card feature sat blocked behind it for 15 days. 10 days passed between the task being assigned and the first commit.

This platform does not fix this problem. The log says clearly that this mess came from a staffing decision, and that the staffing question "was never answered." Limiting work-in-progress and handing off work cleanly are management calls. What the platform can add is visibility — showing, every week, how many days since the last commit on each open branch.

What this evidence changes in the plan

Three things change because of this.

1 · We already have a starting point. Section 06 asked Phase 0 to measure how many bugs escape to production. It is already measured: a bug sits in production for 37 days on average, and up to 171 days for the worst 10%. A third of all commits are fixes for earlier commits. This makes Phase 0 cheaper and gives us concrete targets.

2 · Cross-brand duplication is the biggest win, and it was not in the original plan. At 93% of 705,000 duplicated lines, it is the single largest cost we measured, and the analyser already computes the matching fingerprint. Phase 1 now adds a process for fixing something once and applying it across repos.

3 · Several fixes already exist, they just are not turned on. dead_code, depgraph, exact_duplicates, gitleaks and osv-scanner all exist and pass their tests today. The freeze and intake checkpoints are already verified. This makes us more confident in the Phase 1 estimate, it does not add to it.

What this platform does not fix, plainly

Four of the 39 problems are outside what this can fix. Client self-service documentation is a separate product for a different audience. Staffing and work-in-progress limits are management decisions — the log shows the question was raised and never answered. Waiting on client sign-off, sometimes for weeks, depends on someone outside our team. And using Unicommerce as the source of truth is an existing design choice. It needs its own decision, not a tool.

About 35 of the 39 problems are fixed, fully or partly. Claiming all 39 would be exactly the kind of overstatement this document is trying to avoid.

Finding 0 · A break that passing tests cannot see

fleet swarm creates a real git worktree and starts a real child process — then the child dies while reading its own arguments. child_command.rs:17 builds <exe> __agent …. keel handles that case at main.rs:169. The new workspace's root.rs only mentions __agent in a comment. We reproduced it directly:

All 351 tests still pass, because they swap in a fake binary through FLEET_WORKER_TEST_CHILD_EXE instead of running the real one. This is exactly the failure the project's own PRINCIPLES.md warns about — a proxy is not the property — and it happened inside the very tool built to catch it. Fix time: about one day. The fleet-rs repository shows 570 commits across 7 active days. 360 of those commits — 63% — come from an unattended loop that reran a check script every 30 minutes and committed the same empty marker each time. 05

Why this is a different way of building software, not just faster typing

The usual AI pitch is that a developer writes code faster. That is the claim METR measured, and it turned out false. This is a different claim: the work moves to different hands.

What the machine takes over

  • Writing the spec — turning a conversation into a written contract with acceptance tests, before any code exists
  • Building — many agents, in parallel, each isolated in its own git worktree
  • Checking the work — the kernel re-runs every check itself and never just trusts an agent's claim that tests passed
  • Gating — the analyser blocks changes that are unsafe, too large, or below standard
  • Remembering — every merge writes down what was learned

What stays human, always

  • Deciding what is worth building — and what the client actually meant
  • Judging the result — approving a pull request is something a person is accountable for, and stays that way
  • Anything touching a contract, a migration, or money — always held for a person, by rule, never auto-merged
  • Architecture that spans systems — the machine proposes, a person decides

Measuring honestly — three ways we avoid fooling ourselves

  • Set a baseline before changing anything. Phase 0 runs the collectors against 90 days of existing history before a single change ships. Without a "before" picture there is nothing to compare to, and every later claim can't be checked.
  • Never rely on self-reports. No KPI comes from asking developers if they feel faster. METR's subjects believed they were 20% faster while actually being 19% slower — that gap is exactly why this rule exists.
  • Watch for gaming. Mutation kill rate can be raised by weakening test settings instead of improving tests. Coverage can be raised without testing anything real. Threshold settings are locked, and their fingerprint is recorded with each run, so a lowered bar shows up in the audit trail.

Measurement note that changes the numbers

/usr/bin/time -l reports only the main process. For work that spawns many processes, it shows two to three times less than the real number: cargo test --workspace reports 361 MB from the main process, but actually peaks at 1.18 GB once every rustc and test binary is counted. The figures above count everything. Any sizing based on main-process-only numbers is about a third of what is really needed.

Bottom line: memory is not what limits us. Time and disk space are. No process we measured used more than 1.2 GB, and Fleet's own graph and impact commands barely use any memory at all, 14–27 MB. What actually costs money is time — 6.4 minutes for a full check, 6.5 minutes for the Rust tests — plus disk space per lane.

Three findings from the measurement, in order of cost

1 · The node_modules folder is checked into git. A work lane uses 1.5 GB of disk on average, and one we checked was 1.1 GB, of which 1.0 GB was orb/node_modules. Every new lane copies it before any work even starts. Telling git to ignore this folder removes about two-thirds of the disk cost per lane, and is the cheapest fix in this whole document.

2 · Nothing limits how many lanes can run at once. The 4 GiB RLIMIT_AS caps one lane; nothing caps the total. A search for max_lanes, max_concurrent and semaphores found nothing. Client, contract and supply-chain risk

This section was not in the first draft of this document, and it covers the risk most likely to stop the project. We are a consultancy — the code this platform touches belongs to other companies.

The delete-straight-away agreement is not on by default, and the newest models cannot get it

Under Anthropic's business contract, they do not train on our clients' code by default — that part is fine. Keeping the data is the problem. Normally what we send and get back is held for up to 30 days unless we sign an agreement that they delete our data straight away, which needs approval from Anthropic's sales team for our specific account.

Worse: as of June 2026, under Anthropic's Covered Models policy, the newest, most capable models always keep data for at least 30 days and cannot get the delete-straight-away agreement at all. So an existing agreement can stop covering us the moment we upgrade to a newer model — and nothing tells us that happened.

Even with that agreement in place, Anthropic still keeps some safety-check scores, and on accounts flagged for misuse they can keep the actual content much longer.

How this could fail: it is twelve months on and this did not work

12.1 · Knowledge base — the entry format

One Markdown file per lesson learned. The front matter is read by machines; the body is for people and for search. rule_id is the spine of the whole system. It is what lets a gate finding, a knowledge-base entry, and the repeat-mistake KPI all point to the same thing.

# kb/learnings/2026-09-08-jwt-clock-skew.md
---
id:          kb_01J9X...          # ULID, sortable, never reused
rule_id:     auth.jwt.clock-skew   # THE JOIN KEY. gate findings carry this too
kind:        incident                # incident | decision | client-need | pattern
severity:    high
repos:       [payments-api]
clients:     [acme]                  # empty = applies everywhere
symptoms:    ["401 after deploy", "works locally"]
detector:    semgrep:jwt-no-leeway   # null if not yet mechanisable
created:     2026-09-08
source_pr:   payments-api#4471
supersedes:  null
---

## What happened
Token validation used exact expiry. Two servers drifted 40 seconds apart.
Roughly 3% of logins failed for 20 minutes at 02:00.

## Why it happened
The library defaults to zero leeway. Nobody had read that default.

## The rule now
Every JWT verification passes explicit leeway of 60 seconds.

## How it is enforced
semgrep rule `jwt-no-leeway` — blocking since 2026-09-09.
The field that makes this more than a wiki

detector is what makes the difference. An entry with a detector becomes a check that runs automatically, and the mistake can never happen again unnoticed. An entry without one is just words people may or may not read. The share of entries with a detector, against entries without one, is the health score for the whole knowledge base. It shows how much of what the team learned is actually enforced, not just written down.

12.2 · Post-merge writer — how a merge becomes a learning

This runs as a GitHub Action when code merges to the main branch. It proposes an entry, and a human confirms it. It never writes to the knowledge base by itself, because an unreviewed knowledge base fills with noise and ruins search results — this is pre-mortem failure 2.

Two failure modes that must be handled

Noise. Writing an entry for every merge wrecks search quality within weeks. The four-way trigger condition above is the filter, and it should start narrow and loosen over time — never the other way round.

Near-duplicates. Without the merge step, the store fills up with twenty phrasings of one lesson, and search returns the weakest one. Merge entries above a similarity threshold. Never just append.

12.3 · Indexer and retrieval

This uses both keyword and vector search, because neither one alone is enough: keyword search finds an exact error string, vector search finds a paraphrased idea. About ten lines of code combine the two rankings into one.

fn index(kb_dir):
    for file in kb_dir.glob("**/*.md"):
        fm, body = parse_front_matter(file)
        assert_valid(fm)                          # CI fails on a malformed entry
        # Chunk on headings, not fixed size — "## The rule now" must stay whole
        for chunk in split_on_headings(body, max_tokens=512):
            vec = fastembed.encode(chunk)         # local, CPU, ~200MB RAM
            sqlite_vec.upsert(
                id   = "{fm.id}#{chunk.heading}",
                emb  = vec,
                meta = { fm.rule_id, fm.kind, fm.repos, fm.clients,
                         fm.severity, fm.created, text: chunk }
            )
            tantivy.add(id, chunk)                # the keyword half

fn retrieve(query, repo, client, k=8):
    dense  = sqlite_vec.knn(fastembed.encode(query), k=20,
                            filter = repos.empty or repos.contains(repo))
    sparse = tantivy.bm25(query, k=20)
    fused  = rrf(dense, sparse, k_const=60)       # 1/(60+rank), summed

    # Client-specific context outranks generic advice for that client
    for hit in fused:
        if hit.clients.contains(client): hit.score *= 1.5
        if hit.severity == "high":       hit.score *= 1.2
        age_days = now - hit.created
        hit.score *= 0.5 ^ (age_days / 365)       # year half-life; old truth decays

    return fused.sort_desc().take(k)

12.4 · The analyser gate

Moving from reporting to actually blocking bad merges only needs the last two steps below. Everything above them already exists and passes tests today.

fn gate(pr) -> Verdict:
    changed = git.diff_names(pr.base, pr.head)
    if changed.empty: return PASS

    findings = []
    for collector in POLICY.enabled:         # 33 collectors once 1.1 lands
        try:
            # Diff-scoped: seconds, not minutes. This is what makes it a gate.
            findings += collector.run(scope=changed, timeout=POLICY.timeout)
        catch Timeout or ToolMissing as e:
            # An environment fault is NOT a code failure. Never fail the PR for it.
            findings += Finding(rule="env.fault", severity="info", detail=e)

    # Cross-reference the knowledge base — this is what makes it OUR gate
    for f in findings:
        f.kb = kb.get(f.rule_id)                  # prior context, if any
        f.is_repeat = (f.kb is not null)         # feeds the repeat-mistake KPI

    # Batch-size check — the DORA mechanism, enforced directly
    if diff_lines(pr) > POLICY.max_diff_lines:
        findings += Finding(rule="batch.oversized", severity="warn",
                            detail="{n} lines. Larger changes fail more often.")

    # === the gate itself ===
    blocking = findings.filter(f =>
        POLICY.severity_of(f.rule_id) == "block"
        and f.rule_id not in POLICY.warn_only     # two-week grace per new rule
    )

    post_or_update_comment(pr, render(findings))  # idempotent on re-push
    emit_event("gate.completed", {pr, findings, policy_digest: sha(POLICY)})

    # checked == 0 must FAIL. A run that checked nothing is not a pass.
    if findings.checked_count == 0: return FAIL(exit=6, "no checks ran")
    return blocking.empty ? PASS(0) : FAIL(exit=1, blocking)
Three details that decide whether the gate survives contact with a team

Environment faults never fail a PR. A missing scanner is an infrastructure problem, not a code problem. A gate that blocks merges because a tool wasn't available gets switched off within a week — and rightly so.

Every new rule starts as a warning only. It watches for two weeks to see its false-positive rate before it can block anything. Risk 5 in section 10 explains why.

checked == 0 fails. The most common way to fake a green result is a suite that ran nothing at all.

Security rule for every inbound connector

An issue body, PR description, commit message or webhook payload is data. The kernel acts on the event type, never on the words inside the payload. Is this pull request making the system better or worse?

This was requested directly, and it is the hardest thing in the document to do honestly, because the obvious ways to measure it can all be gamed.

Every PR gets a system impact score: a signed number with a full breakdown, posted as a comment. It is advisory, never blocking. A blocking score would be gamed within a month, and the workaround would be worse than the problem it solves.

fn impact_score(pr) -> Score:
    base = analyse(pr.base_sha)                   # cached — computed once per main commit
    head = analyse(pr.head_sha)

    terms = {
      security:    -8.0 * new_findings(head, base, severity >= high)
                   -2.0 * new_findings(head, base, severity == medium),
      complexity:  -0.5 * (head.avg_cyclomatic - base.avg_cyclomatic),
      duplication: -3.0 * new_cloned_blocks(head, base),
      tests:       +4.0 * (head.mutation_kill - base.mutation_kill)
                          if changed_files.have_tests else -5.0,
      deps:        -6.0 * new_cves(head, base),
      coupling:    -1.5 * (head.max_fan_out - base.max_fan_out),
      debt_paid:   +5.0 * hotspots_removed(head, base)   # reward cleanup
    }

    # Clamp EVERY term. One dimension must never swamp the rest —
    # otherwise deleting a test file swings the score more than a real fix.
    total = sum(clamp(t, -10, +10) for t in terms.values())

    return Score {
      total, terms,
      confidence: if changed_lines < 20:  "low"      # small diffs are noisy
                  elif languages_unsupported: "partial"
                  else: "normal",
      verdict: total > 2  ? "improves"
             : total < -5 ? "degrades — worth a closer look"
             :              "neutral"
    }
Where this is weak, stated plainly

It cannot tell if the feature is correct. Every dimension is structural. A change can score +8 and still build the wrong thing entirely.

Small diffs are noise. Under about 20 changed lines, the score doesn't mean much, which is why confidence is reported alongside it.

It can be gamed if it ever becomes a target. Deleting a complex function scores well. This is exactly why it never blocks a merge and never appears in anyone's performance review. The moment it becomes a target, it stops being a measurement — and that is a rule the team commits to, not something the code can enforce.

Evaluation, observability, and the self-improvement loop

Nothing above proves the system works, or that it gets better over time. Tests prove the code matches the spec. They say nothing about whether the machine's judgment is any good, or whether it is improving. This section covers the setup that answers that.

Most of this already exists — it is simply not wired to anything

Orb already has 19,579 lines of verification tooling that no CI job calls: a Gemini-based judge, 6,500 conversations from published research with records of where they came from, a live-model driver that scores whether replies hand mental effort back to the user, a quality-score module that explains why two candidate tools were rejected on licence and measured discrimination, an ffmpeg audio gate with voice detection, a UX gate over recorded traces, and a 9,728-line human simulator with real recorded audio fixtures.

One example is worth quoting, because it is the whole argument for this section. evals/load_direction/README.md records that the unit tests were "204-green while the running product still handed the load back." A tool built here caught a failure that a green test suite could not see. The work here is to wire that discipline into CI and extend it across Fleet and the gate — not to invent it.

Four layers, because each one catches what the layer below cannot

17.1 · The LLM judge

This runs on every machine-authored pull request, before a human sees it. It never blocks — it only notes and records, because a judge with veto power becomes a target and gets gamed.

fn judge(pr, contract) -> Verdict:
    # Independence rule, same as the verifier: never the model that wrote it
    model = router.resolve(role=Judge, exclude_family=pr.author_model.family)

    v = llm(model, prompt=JUDGE_RUBRIC, input={
        diff:      pr.diff,
        contract:  contract,              # what it was asked to do
        kb_hits:   kb.search(pr.intent),  # what we already knew
        gate:      analyser.findings(pr),
    })
    # The rubric forces a score AND a reason on five fixed axes:
    #   contract_met · scope_creep · reuse_missed · risk_named · test_honesty
    # "test_honesty" asks: do these tests fail if the behaviour changes?
    require(v.scores.all(s => s.reason != null))   # a score with no reason is void
    ledger.append(Receipt{ kind: JudgeVerdict, pr, model, scores: v.scores })
    post_comment(pr, render(v))                     # advisory, never blocking
    return v

17.2 · Capturing what humans rejected — the layer that does not exist today

Every automated signal only shows whether the machine did what it was told. Only a human knows whether that was the right thing to do. When a reviewer changes, rejects or rewrites machine output, that is the most valuable signal the system will ever get — and today it is thrown away.

on pr.review_submitted or pr.closed or commits_pushed_over_agent_work:

    delta = diff(agent_head, human_head)   # what the human actually changed

    if cls.generalises:                   # judged by a second model, not assumed

This is what "self-evolving" actually means here

Not that the model retrains itself. It means a rejection becomes a rule, and the rule becomes a gate. If that rate approaches zero, every month of running the system makes the next month cheaper — and that is the only sense in which this system gets better every month.

Three ways this setup could lie, and the guard for each

The judge drifts. A model scoring another model can be confidently wrong in a correlated way. Guard: agreement with human verdicts is tracked all the time, and a judge below 80% is ignored rather than trusted.

Rejection capture becomes a chore. A form nobody fills in produces no data. Guard: it is one spoken question from Orb at the moment of rejection, in the reviewer's own words, classified afterwards by machine.

Green evals while the product actually fails. This is exactly what load_direction already caught — 204 passing tests against a product that was still failing its users. Guard: at least one check must run against the real running system rather than a mocked one, which is why the human simulator and audio gate stay in the suite even though they are slower.
