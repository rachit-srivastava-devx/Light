## Fresh sweep results

### N-1 (P1) — every line-count gate in the tree is broken, in one of two directions

Both forms executed against a fixture; neither does what its own text claims.

**Form A — cannot fail** (`| awk '$1>80 && $2!="total"'`, exit always 0):
`scan:117`, `planner:117`, `candidate:107`, `verify:163`.

**Form B — cannot pass** (`find … | xargs awk 'END{if(NR>80)exit 1}'`): `xargs` concatenates every
file into one `awk` invocation, so `NR` is the crate total, not the per-file count. Executed:

```
$ seq 1 50 > t/src/a.rs; seq 1 50 > t/src/b.rs      # both files compliant
$ find t/src -name '*.rs' | xargs awk 'END{if(NR>80)exit 1}'
exit=1
```

- `verify/BLUEPRINT.md:184` — `[ ] find crates/verify/src -name '*.rs' | xargs awk 'END{if(NR>80)exit 1}' exits 0 per file` — the words "per file" are false; this exits 1 for any crate over 80 total lines, i.e. always.
- `review/BLUEPRINT.md:184` — same defect, four files piped to one `awk`.

**The correct form is already in the tree.** `probe_business/BLUEPRINT.md:155-158` invokes `awk` once
per file with its own ceiling:

```
[ ] awk 'END{if(NR>80)exit 1}' crates/probe-business/src/lib.rs
[ ] awk 'END{if(NR>70)exit 1}' crates/probe-business/src/probe.rs
```

**Fix:** replace Form A and Form B with the `probe_business` per-file form, or
`find <dir> -name '*.rs' -exec awk 'END{if(NR>80)exit 1}' {} +` is *not* a fix (same concatenation) —
use `-exec … {} \;` or `awk 'FNR==1{…}'` with per-file state.

This is `fleet/PRINCIPLES.md` verbatim — *a check cheaper to fake than to satisfy will be faked* —
and it is the same defect class as the already-closed P1-7 ("clippy gate cannot fail"). `scan` is an
authority node (`scan:126`, "mutation floor is ≥80% for this authority predicate"), so the node most
in need of a real gate still has a decorative one.

**Not P0:** no builder is blocked; the gate is simply worthless. It is P1 because every affected DoD
will be marked green on evidence that proves nothing.

### N-2 (P1) — `route → scan` payload: three documents, three types

| Source | Says the `route -> scan` payload is |
|---|---|
| `EDGE-TYPES.md:17` | `RouteDecision` (owning crate `route`) |
| `route/BLUEPRINT.md:39` | `pub struct RouteDecision { pub selected: CandidateId, pub stages: Vec<StageEvidence>, pub reservation: ReservationRequest, pub snapshot_digest: String }` |
| `scan/BLUEPRINT.md:8` | "Incoming edges: `route -> scan`: admitted `IntentSpec` plus unknowns, effects, acceptance refs, dependencies." |
| `scan/BLUEPRINT.md:83` | "Wire the `route -> scan` adapter without IO → contract test with a typed `IntentSpec` fixture." |

`EDGE-TYPES.md:3-4` declares itself canonical — *"If you find a conflict, fix the blueprint, not this
table"* — so `scan:8` and `scan:83` are the side that is wrong. Worse than a naming slip:

so a builder handed `RouteDecision` cannot construct `ScanInput` without inventing them. `IntentSpec`
is the `intent -> route` payload (`EDGE-TYPES.md:15`), not a `route` output.

**Not P0:** neither type is phantom, and `scan`'s own core (§5 predicate, steps 1-3, all its gates) is
fully specified and buildable in isolation. It is P1 because the composition test `scan:127` demands
("A composition test proves `route -> scan -> dag/probes`") cannot be written, let alone compiled,
until one owner decides which type crosses the edge.
