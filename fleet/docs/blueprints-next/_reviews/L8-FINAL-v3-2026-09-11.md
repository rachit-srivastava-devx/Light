#### Root cause: `-exec … \;` is the one form that discards the utility's exit status

POSIX `find`: for `-exec … ;` the exit status of the invoked utility does **not** contribute to
`find`'s exit status. For `-exec … +` it does ("if any invocation returns a non-zero value as exit
status, the find utility shall return a non-zero exit status"). The brief's instruction — *use `\;`,
**not** `-exec {} +`* — is exactly backwards on the propagation axis.

Isolation control, removing awk from the picture entirely:

```
$ find /tmp/gate-test -name '*.rs' -exec false {} \;
exit: 0
```

`false` cannot be misread. `\;` swallows it.

Confirmed on two independent `find` implementations so this is not a local-shell artifact
(`find` in this shell is a function resolving to `bfs 4.1.1`; `/usr/bin/find` is BSD find on
Darwin 25.6.0 / arm64):

```
$ /usr/bin/find /tmp/gate-test -name '*.rs' -exec awk 'END{if(NR>80){print FILENAME": "NR" lines"; exit 1}}' {} \;
/tmp/gate-test/src/big.rs: 100 lines
exit: 0

$ /usr/bin/find /tmp/gate-test -name '*.rs' -exec awk 'END{if(NR>80){print FILENAME": "NR" lines"; exit 1}}' {} +
/tmp/gate-test/src/big.rs: 100 lines
exit: 1
```

#### But `+` is not the fix either — it reintroduces the v2 concatenation bug

`_reviews/L8-FINAL-v2-2026-09-11.md:104` already called this: with `+`, awk receives many files in one
invocation, `NR` accumulates across all of them, and `END` runs once. Five clean 20-line files trip the gate:

```
$ for i in 1 2 3 4 5; do seq 1 20 > /tmp/gate-test2/src/f$i.rs; done   # every file is 20 lines
$ /usr/bin/find /tmp/gate-test2 -name '*.rs' -exec awk 'END{if(NR>80){print FILENAME": "NR" lines"; exit 1}}' {} +
/tmp/gate-test2/src/f3.rs: 100 lines
exit: 1      <-- false positive; no file exceeds 80 lines
```

So the two forms fail in opposite directions:

| Form | Per-file `NR` semantics | Exit status propagates | Verdict |
|---|---|---|---|
| `-exec … {} \;` (**currently shipped**) | correct | **no** — always 0 | gate is decorative; never fails |
| `-exec … {} +` | **wrong** — `NR` cumulative | yes | gate fires on clean crates |

Neither is a working gate. N-1 remains open.

#### Verified replacement

This form was executed against all three fixtures and is the only candidate that is correct on both
axes (per-file counts **and** exit propagation):

```bash
find <dir> -name '*.rs' -exec awk '{c[FILENAME]++} END{for(f in c) if(c[f]>80){print f": "c[f]" lines"; bad=1} exit bad}' {} +
```

```
gate-test  (one 100-line file)          -> /tmp/gate-test/src/big.rs: 100 lines   exit: 1
gate-test2 (five 20-line files)         -> (no output)                            exit: 0
gate-test3 (3-line file, no final \n)   -> (no output)                            exit: 0
```

`+` is required here for exit propagation; the per-file `c[FILENAME]` map removes the `NR`-accumulation
defect that made `+` unusable before. `exit bad` with `bad` unset is `exit 0`. Batching is safe —
POSIX makes `find` return non-zero if *any* batch invocation does.

Equivalent verified alternative if a `wc`-based form is preferred:

```bash
find <dir> -name '*.rs' -exec wc -l {} + | awk '$2!="total" && $1>80 {print $2": "$1" lines"; bad=1} END{exit bad}'
```
(`gate-test` → exit 1, `gate-test2` → exit 0.)
