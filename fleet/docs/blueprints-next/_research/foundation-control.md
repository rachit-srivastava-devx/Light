## Recommended adoption order

1. **Store:** adopt SQLite through a Fleet-owned port; verify transaction boundaries, WAL settings, busy behavior, crash recovery, and receipt durability before wiring effects.
2. **Control/route:** adopt Tokio for execution and petgraph for DAG mechanics; keep policy, reservations, leases, and deterministic route scoring in Fleet.
3. **Lifecycle:** first convert the current reducer into a pure, persisted transition contract; add Statig only if it removes duplicated illegal-transition code without hiding effects.
4. **Model/connectors:** add ACP, Octocrab, and io-gmail behind capability-probed adapters. Provider credentials, quotas, endpoint-reported identity, and live receipts remain Fleet evidence, not library claims.

## Explicit non-adoption

`smlang 0.8.0` (commit `f9a12bdd17e50f6cb603296949b293d5d1bbdc75`, published 2024-08-09, MIT OR Apache-2.0) is documented as a no-std state-machine DSL, but its published crate is very small and its documentation/release cadence is weaker than Statig for this host-side controller. Keep it as a fallback only; do not add it to the first migration. Source: [crate](https://crates.io/crates/smlang/0.8.0), [repo](https://github.com/korken89/smlang-rs).
