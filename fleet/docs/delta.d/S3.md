# S3 (part 1) — parallel, worktree-isolated role lanes + the CARGO_TARGET_DIR allowlist bug

Backlog item: `handover/BACKLOG.md`, `## [~] S3`. This tick covers item 1 only (parallel lanes).
Item 2 (the reuse/registry gate) is **untouched** — do not read this as S3 being fully done.

## What was actually wrong (confirmed by reading, before touching anything)

- `swarm::dispatch_verified` (`keel/fleet/src/swarm.rs`) loops over the five roles but only bumps
  a lifecycle milestone per role — no process ever runs for Lead/Designer/Verifier/Meter.
- `main.rs::swarm_dispatch_command`'s `--role` path calls `resolve_swarm_roles` (routes all five)
  but then `select_swarm_builder` always discards four of the five routed roles and only executes
  Builder via `run_with_evidence` → `spawn_agent`. The routing comment at the call site said so
  explicitly: *"Real per-role execution is C8; S1 wires and publishes the five allocations."*
- No worktree isolation existed in the dispatch runtime; the only worktree primitive
  (`rollback_artifact`) uses `--detach` + `/tmp`, not `AGENTS.md`'s `.worktrees/<name>` named-branch
  convention.
- `spawn_agent_with_args` (`main.rs`) does `command.env_clear().env("PATH", path)` and only re-adds
  `HOME`/`LANG` — `CARGO_TARGET_DIR` was silently dropped, so any worker spawned through this path
  would rebuild the crate into its own default `target/` instead of the shared cache.

## What this tick built

### 1. `keel/fleet/src/worktree.rs` (new module)

- `create(repo, name)`: `git -C <repo> worktree add -b fleet/<name> .worktrees/<name> HEAD` — a
  **named branch**, not `--detach`, per the task spec and `AGENTS.md`'s own convention.
- `remove(repo, &worktree)`: `git -C <repo> worktree remove --force .worktrees/<name>`, with a
  filesystem fallback (`remove_dir_all`) if git itself fails to leave nothing behind, plus a
  best-effort `git branch -D`/`git worktree prune` so lanes don't accumulate dead refs.
- `unique_name(label)`: `<label>-<pid>-<atomic-counter>` — never a content digest of the task
  alone (`AGENTS.md` rule 4: two concurrent dispatches of the identical task string must not
  collide). Proven directly: `worktree::tests::two_concurrent_names_never_collide`.
- `lane_cap()`: `available_parallelism().saturating_sub(2).clamp(1, 16)` — the exact
  `min(16, cores-2)` formula from the acceptance bar, floored at 1 so a 1–2 core box still runs
  lanes (serially, but correctly).
- **Real bug found while testing, not hypothesized**: concurrent `git worktree add` invocations
  against the *same* repo contend on git's own `.git/index.lock` / `.git/worktrees` administrative
  lock. First run of the 4-lane acceptance test: 3 lanes succeeded, the 4th failed fast (exit 3)
  while the others were still mid-checkout — a transient lock collision, not a real defect in the
  lane logic. Fixed with a bounded retry (8 attempts, cheap dependency-free jitter, `git worktree
  prune` between attempts to clear any partial admin state) rather than serialising `create` (which
  would defeat the whole point of S3) or silently swallowing the failure.

### 2. `swarm_dispatch_command`'s `--role` path now executes 4 of the 5 roles for real

After `resolve_swarm_roles` routes all five roles, the non-Builder four (Lead/Designer/Verifier/
Meter) are run through the new `run_role_lanes_concurrently(repo, task, routed)`:

- batches of up to `worktree::lane_cap()` lanes, each batch run via `std::thread::scope` (every
  batch is joined before the next starts — no leaked threads);
- each lane: `worktree::create` → `spawn_agent(&routed.agent, &lane_repo, task, model)` (the
  **same** re-exec path Builder already used: `fleet __agent <agent> <worktree> <task>`, a real
  subprocess, not a simulated one) → `worktree::remove`, **on every path** (a closure returning
  `Result<i32, i32>`, with cleanup called unconditionally before the outcome is constructed) so a
  faulted lane never leaks a worktree;
- `append_lane_status(role, "running"/"passed"/"failed", ...)` is called from inside each lane
  (real ledger rows, same schema `lane-status.v1.json` already defines — no contract edit needed,
  no ADR required);
- Builder is **not** re-run through this path — it keeps its existing single-repo
  `run_with_evidence` flow unchanged, since `roles::evaluate`'s `LEAD_WROTE_CODE` gate means only
  Builder may write code, and only Builder's diff needs to be frozen against the real repo.

### 3. `spawn_agent_with_args`: `CARGO_TARGET_DIR` allowlist fix

```rust
let cargo_target_dir = env::var("CARGO_TARGET_DIR").ok();
...
if let Some(value) = cargo_target_dir {
    command.env("CARGO_TARGET_DIR", value);
}
```

Read from the parent's actual environment at spawn time — never hardcoded — so it's a no-op when
unset and passes the real value through when set, letting worktree-isolated lanes share one build
cache instead of each silently rebuilding into their own default `target/`.

## The real overlap proof

`spawn_agent_with_args` re-execs `env::current_exe()`. Inside `cargo test`'s own unit-test
harness that resolves to the **test harness binary**, not `fleet` — so a `#[test]` inside
`main.rs` cannot exercise the real re-exec hop (confirmed empirically: the first attempt at this
test failed with `exit=6`, stderr showing the harness's own arg parser choking, not fleet's).
Moved to a Cargo **integration** test instead: `keel/fleet/tests/s3_lanes.rs` drives the real
compiled binary via `env!("CARGO_BIN_EXE_fleet")`, calling a small test-only subcommand
(`fleet __lanes_probe --repo <path> --task <text>`) that builds the four non-Builder
`RoutedRole`s with the deterministic `"stub"` agent (no router, no network/CLI credentials, no
external flakiness) and calls the exact production `run_role_lanes_concurrently`.

Real output from a manual run (`fleet __lanes_probe`, fresh fixture repo, `CARGO_TARGET_DIR` set):

```
lane: role=lead agent=stub started_ms=0 ended_ms=226 exit=0
lane: role=designer agent=stub started_ms=0 ended_ms=243 exit=0
lane: role=verifier agent=stub started_ms=0 ended_ms=206 exit=0
lane: role=meter agent=stub started_ms=0 ended_ms=226 exit=0
exit=0
worktrees remaining: (none)
```

All four lanes start at the same shared-epoch millisecond and their `[started_ms, ended_ms]`
windows overlap by 200+ ms — not sequential (a sequential run would show each lane's `started_ms`
at or after the previous lane's `ended_ms`). The integration test asserts this formally:

```
running 2 tests
test lanes_probe_refuses_cleanly_on_missing_flags ... ok
test four_role_lanes_run_worktree_isolated_and_measurably_overlap_in_wall_clock ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 3.38s
```

`four_role_lanes_run_worktree_isolated_and_measurably_overlap_in_wall_clock` asserts, against real
captured timestamps (not a claim):

1. all 4 roles produce a lane outcome, each exits 0;
2. no `.worktrees/*` entry survives after all lanes complete (leak check);
3. **at least one pair of the four lanes has an intersecting `[started_ms, ended_ms]` window** —
   the direct overlap proof; strictly sequential lanes could never produce this;
4. the batch's total wall time is less than the *sum* of the four lanes' individual durations —
   the corroborating signal that would be false under sequential execution.

Ran this test 3 times back to back (no flakiness observed after the retry-with-jitter fix above):
every run passed. `keel/fleet/tests/s3_lanes.rs` also has
`lanes_probe_refuses_cleanly_on_missing_flags`, proving the probe command itself refuses cleanly
(non-zero exit) on a malformed invocation rather than silently doing nothing.

A Rust unit test (`worktree_lane_cap_respects_the_s3_formula`) separately pins `lane_cap()` to the
literal `min(16, available_parallelism()-2)` formula, and `worktree::tests` cover
create/remove round-tripping, name-collision-freedom, and the cap's bounds directly (no subprocess
involved, so these run fine as ordinary unit tests). `a_failed_lane_never_leaks_its_worktree`
(inside `main.rs`'s own test module) proves cleanup runs on a real error path even though the
"success" path can't be unit-tested for the `env::current_exe()` reason above.
