## What C2 actually checks (read before touching)

"C2 a test wrote production ledger rows." A test that roots `FLEET_STATE` in `mktemp -d` cannot touch
the production ledger, because every path it opens is under a throwaway directory. C2 therefore:

1. **Exempts whole files** whose text contains BOTH `mktemp -d` AND `FLEET_STATE` (`temp_rooted`),
   skipping every line of those files — a narrowing exemption, not a disable.
2. On every remaining line, flags a hit when the file is `.sh`/`.bash`/`.zsh`, the line mentions
   `ledger` (case-insensitive), the line writes (`>>`/`append`/`write`/`open`), and the line does NOT
   mention a safe override (`override`/`LEDGER_PATH`/`ledger_path`).
3. First 8 hits (if any) are printed and it exits 1; otherwise 0.

Hit predicate: `p.suffix in {'.sh','.bash','.zsh'} and ledger-regex and write-regex and not
override-regex`. That predicate is **untouched by B16** — only step 1's *input computation* changed.

## Diagnosis (measured, not assumed)

`temp_rooted(p)` is a full `p.read_text(errors='replace')` and C2 called it **once per yielded line**,
not once per unique file. `_scan.py`'s `lines()` yields `(path, line)` tuples inside a per-file loop,
so a file with N yielded lines is re-read N times — O(lines × bytes) I/O. The current tree makes that
physically expensive: `splitlines()` shreds NUL-containing binaries under `tmp/pdfs/` into tens of
thousands of fake "lines" each (top yielders measured: a 26,101-"line" PNG, a 21,129-"line" PNG, a
15,636-"line" `keel/mutants.out/outcomes.json`), so C2 re-read each multi-MB binary once per fake
line. B15's already-documented estimate of the re-read volume: ~270.8 GB across one pruned walk.

Measured this round, on the working tree B15 left (both runs under identical ambient load — only the
machine's long-stuck Slack renderer at ~1 core and idle claude-code daemons; no verify/corpus/codex
family process, confirmed via `ps aux` before each run):

```
BEFORE  /usr/bin/time -p bash tests/corpus/C2.sh  ->  real > 900.00s: TERMINATED, did not complete
        (measurement timeout at 900s; the gate's own harness records it as
         "TIMEOUT C2.sh exceeded 30s" -> TIMEOUT-PERSISTENT on the serial retry)
AFTER   /usr/bin/time -p bash tests/corpus/C2.sh  ->  real 1.54s  user 1.45s  sys 0.08s  EXIT=0
```

BEFORE >900s (incomplete) → AFTER 1.54s: **well over 500× faster, and 19.5× under the 30s budget**.

Why the before-run is so much worse than the ~270GB model suggests: `read_text(errors='replace')` on
invalid-UTF-8 binary is decoder-CPU-bound, not just I/O-bound, and the read is repeated per fake line
of each binary. The point of the fix is to make the re-read count irrelevant, not to speed up a single
read.

## The ordering assumption — verified, then made robust anyway

`paths` are structurally yielded line-contiguous: in `_scan.py`'s `lines()` the `for number, source in
enumerate(...)` inner loop sits inside the per-file `for name in files` loop, so a generator cannot
interleave two files' lines. Confirmed empirically with a full-walk probe: **888 unique paths,
939,731 total lines, zero non-contiguous paths.**

Because a per-path cache is provably correct even if that assumption ever breaks (e.g. a `_scan.py`
refactor that re-visits a directory), the fix uses a **dict cache (path → temp_rooted result)** — the
"works regardless of ordering" variant — rather than a last-path comparison. It costs the same and its
correctness does not rest on generator ordering.

## Fix (C2.sh only — 6 lines; the hit predicate is byte-for-byte untouched)

`temp_rooted` exists only inside `C2.sh`'s own Python heredoc — it is not a `_scan.py` helper, and no
other detector calls it — so this is a detector-local change, not a shared-infra one. (Surveyed all
`_scan.py` users: T2.sh and H1.sh read each `.sh` file once per unique path via `rglob`; C19.sh
re-reads only files literally named `package.json` per line — bounded and negligible, honest note,
not touched, out of scope.)

```diff
 def temp_rooted(path):
  try: t=path.read_text(errors='replace')
  except OSError: return False
  return ('mktemp -d' in t) and ('FLEET_STATE' in t)
+rooted_cache = {}
 for p,ln,s in lines(root):
- if temp_rooted(p): continue
+ rooted = rooted_cache.get(p)
+ if rooted is None:
+  rooted = temp_rooted(p)
+  rooted_cache[p] = rooted
+ if rooted: continue
  if p.suffix in {'.sh','.bash','.zsh'} and ... (unchanged hit predicate)
```

Equivalence is by construction: `temp_rooted` is a pure function of a path's file content (read-only,
deterministic), so one evaluation per path returns the same value the per-line version would have
returned on every line of that path — the exempt set is identical, just not recomputed quadratically.

## Real correctness proof (not a proxy)

- **Full-tree memo-vs-fresh equivalence:** walked the whole tree once, and for all **888 unique
  paths** the memoized value equals a fresh `temp_rooted(p)` re-computation. Same exempt set, exactly
  3 rooted files. Whole-file re-reads drop **939,731 → 888** (a **1058×** reduction).
- **Fixture controls (positive + 3 negatives) run against the fixed logic over a scratch tree:**
  a genuine `.sh` writing `>> $FLEET_LEDGER` with no override → **caught**; a temp-rooted
  (`mktemp -d` + `FLEET_STATE`) `.sh` writing the same line → **exempt**; a `LEDGER_PATH`-guided
  `.sh` → **exempt**; the same text in a `.txt` → **ignored**. All four behaved as designed.
- **Gate-level verdict set:** the before↔after corpus logs differ only in (a) C2's lifecycle
  (timeout → clean pass) and (b) M2's refused-file count 67006 → 67007, which is the
  `var/b16-after-corpus.log` file I redirected into the tree (M2 counts every file, both refuse
  identically >15000, verdict unchanged). Every A1/S6/S9/T6/M2/M6/M7 line is otherwise byte-for-byte
  identical.
