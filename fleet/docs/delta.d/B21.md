# B21 — mutation gate harness fixed; real score obtained; a genuine, pre-existing coverage regression surfaced

## What was broken

`bin/mutants-gate.sh` scoped `cargo-mutants`'s isolated build copy to `keel/` (via
`--manifest-path keel/Cargo.toml`), but the crate's own test suite needs two things outside that
subtree: repo-root `agents.toml`/`skills.toml` (`agent.rs::load_default`, `skills.rs::load_default`,
both resolve via `env!("CARGO_MANIFEST_DIR")/../../<file>`, absent in the isolated copy) and
`python3` on PATH (`sow.rs`'s `Command::new("python3")`, not resolved the same way inside
`cargo-mutants`' isolated subprocess environment). The unmutated baseline test run failed before a
single mutant was ever tested — confirmed by re-running `cargo mutants` directly with full,
untruncated logging (the gate script's own truncated log hid this). Zero mutation data had been
produced since the `164/232` floor was measured on commit `ba144e2` ("D26", 2026-08-24).

## The fix

Switched `bin/mutants-gate.sh` to `cargo mutants --in-place` — tests directly in this checkout,
where `agents.toml`/`skills.toml`/`python3` all already resolve correctly, instead of an isolated
copy. Tradeoff, documented inline in the script: `--in-place` mutates real source files one mutant
at a time, so it cannot safely run with `--jobs>1` (concurrent mutants would corrupt each other's
edits — cargo-mutants actually rejects `--jobs` + `--in-place` together outright, confirmed by a
real `exit=1` error caught mid-merge and fixed). Forced to serial, meaningfully slower than the old
(broken) `--jobs 4` copy mode — a real full run over `fleet/src/ratchet.rs` took roughly 2.5 hours
serial on this machine.

**Real, hard requirement observed:** never run `verify.sh` or any other `cargo build`/`cargo test`
touching `keel/` while an `--in-place` run has a live mutation applied (checked via
`git diff --stat keel/fleet/src/ratchet.rs` throughout) — doing so would build/test a
mutated version of the file by accident. Caught and avoided this exact race once during this
session (killed a concurrently-launched `verify.sh` before it could touch the mutated file).

## The real result

```
mutants: caught=185 total=266 floor=164/232
mutants: REFUSE: mutation score dropped: 185/266 < 164/232
```

- Old floor (2026-08-24, commit `ba144e2`): 164/232 caught = **70.69%**
- New real score (2026-09-03, this fix): 185/266 caught = **69.55%**

The absolute caught count is HIGHER (185 vs 164) — `ratchet.rs` grew by 34 testable mutants since
Aug 24 (real feature commits across multiple sessions since then: `git log -- ratchet.rs` shows
lanes `t-heal`, `q-ux`, `z-evid`, `k-A`, and others landed in between). But the *ratio* dropped by
about 1.1 percentage points, meaning test coverage did not keep pace with the new code added to
this file — a genuine, real regression, not a broken measurement.

**Deliberately NOT done:** `bin/mutants-floor.txt` was NOT updated to `185/266`. The mutants stage
is `advisory` in `verify.sh` (not `required`), so this REFUSE does not block any commit — but
silently rewriting the floor to match a real regression is exactly the "quietly lower the bar"
failure mode this project's own doctrine refuses to allow (a check whose bar moves to match
whatever the code currently does asserts nothing). The gate's REFUSE here is correct behavior, not
a bug to route around.

**What's needed to actually close this (tracked as B23, not done in this tick):** the specific
missed mutants weren't preserved for this run — `bin/mutants-gate.sh`'s own `trap cleanup EXIT`
deletes its `mktemp -d` output directory (including `missed.txt`) as soon as the script exits,
which is correct for a routine pass/fail gate but means a REFUSE here doesn't leave anything to
triage afterward. A follow-up run should either capture `missed.txt` before cleanup on a REFUSE, or
be run with `--output` pointed at a durable path, so the specific uncovered mutants can be read and
matching tests written.

## Why this is real, not noise

Confirmed the comparison logic itself (`bin/mutants-gate.sh`'s `[ $((caught * floor_total)) -lt
$((floor_caught * total)) ]` cross-multiplication) is correct: `185*232=42920` vs `164*266=43624` —
`42920 < 43624`, so the ratio genuinely dropped. This was independently re-derived by hand, not just
trusted from the gate's own printed message.
