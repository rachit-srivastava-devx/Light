## The gap, precisely

`bin/lanes.conf` holds extra failover lanes past the built-in default (`api.llm7.io`). Each record
is `url|model[|dialect]`. `bin/freelane.sh` reads them, and for each one builds a request body
shaped by `dialect` (`openai` sends `{"model","messages"}`, reply from `choices[0].message.content`;
`prompt` sends `{"model","prompt"}`, reply from `.response`) and parses the reply the same
dialect-aware way. Before the fix documented in `bin/freelane.sh`'s own header comment, the
DevToolBox lane wanted `{"prompt":...}` but was always sent the OpenAI shape, so it answered HTTP
400 `Missing "prompt" field` on every real call — a lane that had never once worked, sitting in
`bin/lanes.conf` for a day, because **nothing in the corpus exercised `bin/lanes.conf` through
`bin/freelane.sh` at all.** A hand `curl` against the same URL with the *correct* body would have
looked perfectly healthy the whole time — proving the raw endpoint is reachable proves nothing
about whether `freelane.sh`'s own dialect wiring for that lane is correct. That is the exact gap
item 3 names.

## What `tests/corpus/M11.sh` actually does

For each real `url|model[|dialect]` record parsed out of `bin/lanes.conf` (same comment-stripping /
blank-skipping / `|`-requiring rule `add_lane()` uses, deliberately re-implemented rather than
sourced — the point is to feed `bin/freelane.sh` independently-derived input and watch what IT
does, not to reuse its own parsing as the oracle):

1. Force the built-in default lane to fail **instantly** (`FREELANE_URL=http://127.0.0.1:1/...`,
   connection-refused, no network round trip) so the *only* lane `freelane.sh` can possibly answer
   through is the one record under test — fed back in verbatim via `FREELANE_LANES`, with
   `FREELANE_CONFIG=/dev/null` so the real `bin/lanes.conf` is not also loaded a second time behind
   it.
2. Run the real `bin/freelane.sh` against that isolated pair of lanes with a real prompt.
3. Assert three things from `freelane.sh`'s own self-reported trace (not a side-channel probe):
   exit 0; the trace's `tried=...` list shows `<that lane's host>:answered`, not some other lane;
   and `resolved_model=` is present and is not the literal `UNRESOLVED` sentinel (an endpoint that
   never reports which model answered is not a countable lane per `bin/lanes.conf`'s own header
   comment).

A lane that fails any of those three is CAUGHT and printed by name. The denominator is the number
of real lane records found in `bin/lanes.conf` (currently 2); an empty file is a failure
("measuring nothing"), not a vacuous pass. Excluded (exit 77), not counted either way, when
`bin/freelane.sh`/`bin/lanes.conf` are missing, `curl`/`python3` are absent, or a reachability probe
against the built-in default lane's own host shows no outbound network at all in this sandbox (a
network-absent environment cannot exercise ANY real lane — that is an environment fact, not a lane
defect).

## Self-assessment (do not grade your own work)

M11 depends on live network access to the two real third-party endpoints in `bin/lanes.conf`. That
makes it the first network-dependent detector in this corpus, with the flakiness that implies: a
transient rate-limit or outage on either provider will make M11 fail (correctly reported as
`CAUGHT`, with the real reason string) even though `bin/freelane.sh`'s wiring is fine. This is the
same category of flakiness `bin/lane-probe.sh` (the pre-existing keyless-endpoint prober) already
accepts, and it is inherent to testing "does this lane actually answer" rather than "does this URL
respond to *some* request" — a check that stubbed out the network would be back to the exact hand-curl
blind spot this item exists to close. The network-absent path is handled (exit 77, excluded), but a
*degraded-but-technically-reachable* third-party endpoint (e.g. answering with an unexpected body
shape rather than clearly failing) could still produce a confusing `unparseable-response` reason on
a lane that is not really broken — the reason string is real either way, but a human reading a red
M11 needs to check whether it's `freelane.sh`'s wiring or the provider having a bad moment.
