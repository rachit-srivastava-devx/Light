# B15 — corpus detectors are individually slow even uncontended: the unpruned shared build tree

Backlog item: `handover/BACKLOG.md`, `## [ ] B15`. "~25 corpus detectors are genuinely slow, even
completely uncontended." Acceptance: either (a) share one tree-walk result across all `_scan.py`-based
detectors, or (b) show with real timing data that per-detector re-walking is not the dominant cost and
name the actual one. Raising `FLEET_DETECTOR_TIMEOUT` is explicitly disallowed (PRINCIPLES.md #11).

## Diagnosis (measured, not assumed) — this is acceptance path (b)

The re-walk-per-detector theory is **real but not the dominant cost.** A single `lines()` walk over the
whole repo — one walk, no detector attached — took **68.75s** (77,112,396 yielded lines). That one walk
alone already exceeds the 30s timeout, so no shared cache could ever have made the first detector pass:
caching would still be walking the same tree once. The dominant cost is *what the walk descends into*.

Decomposing what `lines()` actually yields (950-line walk, bulk I/O):

```
BEFORE (PRUNED_DIRS as committed):
  target-shared/ : 76,173,186 lines (98.8%) · 19,806 files (96.4%) · 4,362.5 MB read
  everything else:    939,209 lines          ·   891 files      ·    45.9 MB read
  single walk:        77,112,396 lines in 68.75s  (real: `time python3 ... lines(root)`)
```

`target-shared/` is the shared `CARGO_TARGET_DIR` that `AGENTS.md` mandates
(`CARGO_TARGET_DIR="$PWD/target-shared"`). It is **not** in `PRUNED_DIRS` (which contains the exact
name `"target"` but not `"target-shared"`), so every `_scan.py` `lines()` call walks the entire Rust
build-artifact tree: `debug/incremental/**/dep-graph.bin` files read as text "lines" of a million-plus
each, `.rlib`s, `query-cache.bin`, etc. This is the **same failure class D30 documented** ("a 4.9GB
CARGO_TARGET_DIR was created outside the pruned paths and 24 detectors began walking it"), re-encountered
under the name `target-shared` that the current worktree convention introduced. This is also exactly why
B13's 25 `TIMEOUT-PERSISTENT` detectors are individually slow **uncontended**: each of the 25 `_scan`
users needed >68s just for its input.

## Fix (one line, shared infrastructure only)

```diff
 PRUNED_DIRS = {
     ".codebase-memory",
     ".git",
     ".venv",
     "__pycache__",
     "docs",
     "node_modules",
     "site-packages",
     "target",
+    "target-shared",
     "tests",
     "var",
 }
```

`tests/corpus/_scan.py` only. No detector script (`tests/corpus/[A-Z]*.sh`) touched; `route.rs`,
`crew/crew/adapters/`, `main.rs`'s `plan_command`/router code untouched; `run.sh` untouched;
`MANIFEST.sha256` untouched (`_scan.py` is not hashed by the D28 integrity gate — verified:
`detector-integrity: 105 detectors match the manifest (denominator: 105)`).

AFTER the fix, a single walk is **939,209 lines in 1.154s** (real `time` run) — 82× fewer lines,
~60× faster, per walk.

## C2 — named separately, not fixed (out of B15's reach without touching a detector)

C2's dominant cost is **not the tree walk.** Its Python calls `temp_rooted(p)` (a full
`p.read_text()`) **once per yielded line, not once per unique file**, giving O(lines × bytes) I/O per
file: a measured **270.8 GB re-read** across `lines()`'s output. Two contributing causes:

1. **77% of yielded "lines" (730k of 939k post-prune) come from NUL-containing binary files**
   (`tmp/pdfs/*.png`, `*.jpg`) that `splitlines()` explodes into tens of thousands of "source lines"
   each; C2 then re-reads the whole 1.1 MB PNG per line.
2. Even with binaries excluded, the quadratic re-read over real large text files
   (`keel/mutants.out/*.json`, `tmp/pdfs/*.txt`, `keel/fleet/src/main.rs`) totals ~25 GB — an actual
   simulation of C2 against a binary-skipping `lines()` finished in **29.55s**, sitting on the 30s
   knife edge, which is not a fix.

The true fix is a ~3-line memoization (`seen=set()`) inside C2.sh — a detector-local change. B15's task
explicitly forbids touching `tests/corpus/[A-Z]*.sh` logic, and a broadened shared-infra input filter
(binary-skip) both changes what 24 detectors' input is for no gate-fixing benefit and still does not
bring C2 under 30s. So C2 is diagnosed and left as an honest `TIMEOUT-PERSISTENT`, tracked as the one
remaining corpus red the 30s-per-detector allocation cannot absorb. Follow-up suggestion, listed, not
acted on: memoize per-file reads in C2 and each `_scan`-family detector (the shared `lines()` interface
cannot fix a detector that bypasses it with its own `read_text`).

## Corpus is still red, and why that is not a B15 failure

`caught=8` → `run.sh` exits 1 → `corpus` (and therefore `verify.sh`) stays red. All eight are
pre-existing conditions that B15's fix only surfaces/honors, none introduced by it:

- A1, S6, S9, T6 — real findings in the current tree (previously timeout-masked).
- M2, M6, M7 — independent real failures present before this change (M2 is the artifact-in-repo refusal;
  note the policy tension: `AGENTS.md` mandates `CARGO_TARGET_DIR="$PWD/target-shared"` inside the repo,
  which is exactly the >15000-file condition M2 refuses on).
- C2 — separate quadratic-re-read defect above.

B15's acceptance is path (b) with real timing: per-detector re-walking was not the dominant cost; the
unpruned 4.3 GB shared build tree was, it is now pruned, wall-clock dropped 1506s→97s with `checked=34`
unchanged. The timeout was not raised. The detectors that genuinely fail fail for real, named reasons.
