# B13 — the corpus gate cannot tell "machine busy" from "code broken"

Backlog item: `handover/BACKLOG.md`, `## [ ] B13`. Elevated to the sole remaining blocker for
landing any commit in this repo per S2b's note in `handover/PROGRESS.md` (`.githooks/pre-commit`
`exec`s `verify.sh` unconditionally; `swarm` was fixed in S2b, leaving `corpus`/B13 as the only
red stage).

## Diagnosis (confirmed, not assumed)

`tests/corpus/run.sh` ran each of the 103 detector scripts under `timeout
"${FLEET_DETECTOR_TIMEOUT:-30}"`. Exit 124 (timeout) was folded straight into `drc=1`, the exact
same code path as a detector that actually asserts its bad-fixture failure. The printed line said
`TIMEOUT ... exceeded 30s -- treated as FAILED`, but the `DENOMINATOR` line and the gate's exit
code made no distinction from a real caught regression — both were just `caught`. Under this
project's normal operating mode (multiple agents/verify.sh instances running concurrently),
detectors that walk the whole tree (`_scan.py`'s `lines()`, used by roughly a third of the corpus)
time out from CPU starvation, not from the code actually regressing, and the previous script could
not tell the two apart. This was independently reproduced earlier this session (S1 baseline: 14
passed/4 failed under contention vs 16 passed/2 failed uncontended, same code).

## Fix

`tests/corpus/run.sh`: a first-pass timeout is now **provisional**, not final. Timed-out
detectors are queued (`timed_out_files`) instead of counted immediately, and after the main loop
finishes (so the retry is no longer competing with the rest of *this run's own* detectors for
CPU), each queued detector gets exactly one serial retry via the same `run_one()` helper. The
retry's outcome is classified into three distinct, explicitly labeled buckets, each reported on
its own line and folded into a wider `DENOMINATOR` line:

- **`TIMEOUT-CONTENTION`** — timed out on the main pass, passed clean (rc=0) on the serial retry.
  Consistent with CPU contention, not a broken detector. **Still fails the gate** (see exit logic
  below) — a timeout is never silently converted to a pass, it just gets a label a human can tell
  apart from a confirmed regression at a glance.
- **`TIMEOUT-CONFIRMED-CAUGHT`** — timed out on the main pass, then genuinely failed (rc=1, not a
  further timeout) on the uncontended retry. Counted as `caught`, same as any other regression.
- **`TIMEOUT-PERSISTENT`** — timed out again on the retry, with nothing else running concurrently
  in this script. This is the "genuinely hanging detector" case from the acceptance bar. Counted
  as `caught`.

Exit logic: `caught > 0` → exit 1 (unchanged meaning: a real regression, confirmed or plain).
`caught == 0 && timeout_contention > 0` → exit 5 (new: the run only saw contention-flavored
timeouts, no confirmed regression, but the gate **still fails** — never a silent pass). Otherwise
exit 0. The `DENOMINATOR` line was extended with `timeout_contention=`, `timeout_confirmed=`, and
`timeout_persistent=` counts alongside the existing `checked`/`total`/`excluded`/`caught`, so the
full breakdown is always published, per PRINCIPLES.md #12 ("publish the denominator").

Nothing about the non-timeout path changed: a detector that fails immediately (rc=1, no timeout at
all) is still reported and counted exactly as before — never routed through the timeout machinery.

`tests/corpus/MANIFEST.sha256` was regenerated (`bin/detector-integrity.sh --update`) because
`run.sh` itself is one of the hashed files (D28's detector-integrity check treats a hash mismatch
as a refusal, so this update is required and deliberate, not incidental).

Files touched: `tests/corpus/run.sh`, `tests/corpus/MANIFEST.sha256`. No detector script
(`tests/corpus/[A-Z]*.sh`) was touched, and `route.rs`, `crew/crew/adapters/`, and `main.rs`'s
`plan_command`/router code were not touched.

## Mutation-test proof, both directions (real output, isolated scratch harness)

Ran the real `run.sh` (a copy, unmodified) against synthetic fixture detectors in an isolated
scratch directory (not committed — `tests/corpus/` is never edited beyond `run.sh` and the
manifest), with `FLEET_DETECTOR_TIMEOUT=2` so the test finishes in seconds instead of tens of
seconds. Verified via `ps aux` that no other `verify.sh`/`corpus`/`cargo` process was running
before each of these runs.

**Direction (a) — a genuinely hanging detector must still be caught, not silently ignored.**
`ZZ-HANG.sh` (`sleep 999; exit 0`) alongside `ZZ-BROKEN.sh` and `ZZ-CONTENTION.sh` (below):

```
$ FLEET_DETECTOR_TIMEOUT=2 bash run.sh
ZZ-BROKEN: assertion failed (this is the fixture's intended failure)
  TIMEOUT ZZ-CONTENTION.sh exceeded 2s on the main pass -- provisional, queued for one serial retry
  TIMEOUT ZZ-HANG.sh exceeded 2s on the main pass -- provisional, queued for one serial retry
-- retrying 2 timed-out detector(s) serially, one at a time, once each --
ZZ-CONTENTION: clean on this invocation
  TIMEOUT-CONTENTION ZZ-CONTENTION.sh -- timed out on the main pass, PASSED CLEAN on serial retry (consistent with CPU contention, not a broken detector). Still fails the gate; rerun uncontended to confirm before trusting this label.

  TIMEOUT-PERSISTENT ZZ-HANG.sh -- timed out again on an uncontended serial retry: a genuinely hanging detector. Counted as a caught regression.
DENOMINATOR checked=3 total=3 excluded=0 caught=2 timeout_contention=1 timeout_confirmed=0 timeout_persistent=1
EXIT_CODE=1
```

`ZZ-HANG.sh` was reported as `TIMEOUT-PERSISTENT`, counted in `caught`, and the run exited 1 (gate
fails). A hanging detector is caught, never converted to a silent pass.

**Direction (b) — a genuinely broken (non-hanging) detector must be caught as a failure, not
misreported as a mere timeout.** `ZZ-BROKEN.sh` (`echo "..."; exit 1`, no sleep at all) in the
same run above: it never appears in any `TIMEOUT*` line. It is printed and counted exactly like
any ordinary caught detector (`checked`, `caught`), through the untouched non-timeout code path.
Confirmed directly: assertion failures are indistinguishable from the pre-existing behavior because
they never enter the timeout branch at all.

**Bonus — the new `TIMEOUT-CONTENTION` label, isolated, to show it alone still fails the gate.**
`ZZ-CONTENTION.sh` uses a marker file to simulate "slow only because something else was
competing for CPU the first time, fast and clean once that has passed" (`sleep 10` before the
marker exists, instant afterward) — run alone, with no other fixture present:

```
$ FLEET_DETECTOR_TIMEOUT=2 bash run.sh
  TIMEOUT ZZ-CONTENTION.sh exceeded 2s on the main pass -- provisional, queued for one serial retry
-- retrying 1 timed-out detector(s) serially, one at a time, once each --
ZZ-CONTENTION: clean on this invocation
  TIMEOUT-CONTENTION ZZ-CONTENTION.sh -- timed out on the main pass, PASSED CLEAN on serial retry (consistent with CPU contention, not a broken detector). Still fails the gate; rerun uncontended to confirm before trusting this label.
DENOMINATOR checked=1 total=1 excluded=0 caught=0 timeout_contention=1 timeout_confirmed=0 timeout_persistent=0
EXIT_CODE=5
```

`caught=0`, yet `EXIT_CODE=5` (not 0) — a pure contention-timeout still fails the gate, distinctly
(exit 5, not 1), never silently converted to a pass. This satisfies acceptance bar item 2
concretely: the label alone is not what fails the gate, the exit code does, and it is never 0.

Fixture scripts and their exact content are pasted above in full; they were not committed to
`tests/corpus/` (that directory is the real gate's detector set, not a place for throwaway
fixtures) — they lived only in a scratch directory for this proof and were run for real, not
simulated.

## `bash tests/corpus/run.sh` alone, uncontended (real repo, real detectors)

Checked `ps aux | grep -E "verify\.sh|corpus|cargo (build|test)|cargo-mutants"` immediately before
running — empty, nothing else running. Ran to completion (~19 minutes wall clock — 34 detectors
each waited out the full 30s timeout on the main pass, then again on the serial retry).

```
DENOMINATOR checked=34 total=34 excluded=69 caught=28 timeout_contention=0 timeout_confirmed=0 timeout_persistent=25
```

(`total=` here reproduces the pre-existing script's convention of printing `total - excluded`, not
raw file count — 103 detector files minus the 69 `NOT MECHANISABLE`/excluded ones is 34, matching
`checked`.)

**Honest reading of this result, not just the mechanism's claim about itself:** every one of the
25 timed-out detectors was `TIMEOUT-PERSISTENT` — none cleared on the uncontended serial retry
(`timeout_contention=0`). That means, on this machine, right now, these ~25 detectors (mostly the
ones that call `_scan.py`'s tree-walking `lines()` over the whole repo) genuinely take longer than
30 seconds even with **nothing else running**. That is a real, separate finding, not a success of
this fix — B13's job was to make a timeout *distinguishable*, not to make detectors faster, and it
correctly did not misreport this as "probably just busy": `TIMEOUT-CONTENTION` stayed at zero, and
all 25 are honestly counted as `caught` failures. The likely root cause (large uncounted
directories under the walk, e.g. `docs/` now carrying 190+ `REVIEW-*.md` files, or `_scan.py`'s
per-file Python overhead across a large tree) is a legitimate follow-up, tracked separately below
— it is not something this fix should paper over by lengthening the timeout unilaterally.

## What this does and does not close

- Closes B13's acceptance bar: timeout vs caught regression are now distinctly labeled and
  exit-coded, the gate never silently passes on a timeout, the denominator is fully published, and
  both mutation-test directions were run for real with pasted output.
- Does **not** close the underlying "why are ~25 detectors individually slow, even alone" question
  — that surfaced *because* B13's fix is honest, not despite it. Worth its own backlog item:
  candidate detectors are the ones sourcing `_scan.py`'s `lines()` (a full-tree walk per detector,
  no shared cache across the 34 detectors that each re-walk the tree from scratch).
- Does not fix `corpus`'s red status — that was never B13's job; B13 is about telling "busy" from
  "broken" apart, and having done so honestly here, the honest answer is "broken (slow), not
  busy" for the currently-timing-out detectors.

## Self-assessment (PRINCIPLES.md #14 — do not grade your own work)

The mechanism is a heuristic, not proof: a detector that is flaky *and* slow could show the same
"fails once under load-like conditions, clears on a later single retry" shape that
`TIMEOUT-CONTENTION` reports, without contention actually being the cause. The fix is honest about
this in its own inline comment and in the printed message ("rerun uncontended to confirm before
trusting this label") rather than asserting certainty it doesn't have. It cannot be gamed toward a
pass — `TIMEOUT-CONTENTION` still fails the gate — but it could in principle mislabel a real,
non-hanging-but-flaky bug as contention if that bug's symptom happens to look identical to
contention on a single retry. A stronger version would retry N times and require unanimity; this
implementation deliberately matches what the backlog item asked for ("re-run ... once") rather
than gold-plating beyond the brief.
