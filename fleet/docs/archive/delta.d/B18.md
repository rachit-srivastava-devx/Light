# B18 — M2: relocate the build cache out of the repo (owner decision) and what it exposed

Closes B17's scoped-out item 1 (M2, `docs/delta.d/B17.md` §M2, §§ "What B17 does NOT commit" #1)
under the owner's explicit decision: shared `CARGO_TARGET_DIR` moves from the in-repo
`$PWD/target-shared` to the repo-external **`$HOME/.cache/fleet-rs-target-shared`**.

Standing law observed everywhere below: no detector predicate was weakened; `tests/acceptance/*`
and `contracts/*.json` untouched (see below for why touching acceptance is the *new* blocker);
`AGENTS.md` and `.gitignore` edits only.

## What changed

- **`AGENTS.md`** — the worktree `CARGO_TARGET_DIR` export line changed from
  `export CARGO_TARGET_DIR="$PWD/target-shared"` to
  `export CARGO_TARGET_DIR="$HOME/.cache/fleet-rs-target-shared"`, with prose added mandating an
  **absolute, repo-external** path. The `$PWD`-relative form was the direct cause of an earlier
  real bug: an agent exporting it from inside `keel/` materialized a duplicate `keel/target-shared`
  (see `docs/delta.d/S2-fix.md`) — an absolute path removes that whole error class.
- **`.gitignore`** — the comment line updated to reflect that `CARGO_TARGET_DIR` now lives outside
  the repo at `~/.cache/fleet-rs-target-shared` (the stale `target-shared/` / `var/target-shared/`
  ignore entries were left in place: harmless, and removing them is not worth a debate).
- **Artifacts physically moved out of the repo** (all `mv`, preferring preserve-cache over
  `rm -rf`): `target-shared/` → `$HOME/.cache/fleet-rs-target-shared`; `keel/target/` (a stale
  build tree from builds run without the export) → `$HOME/.cache/fleet-rs-target-shared-keel-target`;
  `crew/.venv/` → `$HOME/.cache/fleet-rs-target-shared/.venv-crew-saved`; `keel/mutants.out/`
  (untracked, gitignored, regenerable) → `$HOME/.cache/fleet-rs-target-shared/mutants.out`.
- **Reverted a near-mistake:** `keel/mutants.out.old/` is **tracked in git** (107 committed files,
  the D26 mutation-score landmark `ba144e2`), not disposable cache; I initially `mv`'d it too, then
  restored it. Untracked `keel/mutants.out` (0 tracked files) is the genuinely disposable one.

## Real proof it works (not assumed)

1. **Build truly lands in the cache, not the repo.** With the export set,
   `cargo build --manifest-path keel/Cargo.toml -p fleet` completed (`Finished dev profile`) and
   produced `~/.cache/fleet-rs-target-shared/debug/fleet`; `keel/target` was **not** re-created.
   No in-repo `target/` or `target-shared/` exists after the build.
2. **M2 passes:** `bash tests/corpus/M2.sh` → `exit 0`. Tree count dropped 67,017 → **6,817**
   paths (real source + `.git` + untracked scratch), far under the 15,000 cap.
3. **Corpus uncontended-denominator** (real run, twice — once mid-session, once after all changes
   settled; the machine was under sustained heavy CPU load from an unrelated project's rustc build
   farm throughout, so "uncontended" is about this repo, not the box):
   ```
   DENOMINATOR checked=31 total=31 excluded=72 caught=1 timeout_contention=0 timeout_confirmed=0 timeout_persistent=0
   ```
   `caught=1` is exactly the one out-of-scope T6 hit (`bin/codex-tick.sh:43`) B17b left. M2, the
   last red count, is gone. No `timeout_contention` despite the external load. (checked 34→31 /
   excluded 69→72: the freed M2 detector now classifies with the excluded/non-mechanisable set —
   same total 103, one fewer live catchable.)

## What verify exposed — a NEW blocker on the same seam B17 flagged

`FLEET_MUTANTS=0 bash verify.sh` (with the export set, so cargo stages build into the external
cache) **is NOT green**: 3 required stages fail —

```
  FAIL acceptance     (see var/verify.log)
  FAIL readme         (see var/verify.log)
  FAIL swarm          (see var/verify.log)
```

Root cause, definitive, from `var/verify.log`:
```
== P0 acceptance ==
  FATAL: /…/fleet-rs/keel/target/debug/fleet not built
```

The **protected acceptance suite hardcodes the in-repo binary path**:
`tests/acceptance/p0.sh:21`, `tests/acceptance/readme.sh:16`, `tests/acceptance/swarm.sh:15` all set
`FLEET="$ROOT/keel/target/debug/fleet"`; `p0.sh:57` also hardcodes
`tests/tools/b3oracle/target/debug/b3oracle`. With `CARGO_TARGET_DIR` external, cargo never writes
`keel/target/`, so the binary is never at the path the suite demands. This is **agreed-unsatisfiable**
while hard rule 1 ("NEVER edit `tests/acceptance/*`") and the owner's relocation decision both stand:
- `CARGO_TARGET_DIR` external → acceptance/readme/swarm can't find the binary → those stages FAIL;
- `CARGO_TARGET_DIR` in-repo → acceptance finds it but the ~29k-file `keel/target` re-trips M2 → corpus FAILS.

They cannot both be green under the current code. This is the concrete form of B17's warning
("AGENTS.md explicitly mandates the in-repo target-shared … an architecture decision for the
owner"): the acceptance suite is the reason the in-repo path was load-bearing. Symlink tricks were
considered and rejected (Python 3.13 `Path.rglob` follows directory symlinks, so a `keel/target`
symlink re-counts the cache's files into M2; a single-file symlink for the binary would be a harness
shim, exactly the kind of gaming hard rule 1 exists to forbid).

**Resolution options — all owner decisions:** (a) relax hard rule 1 for the *path variable only* so
acceptance/readme/swarm honor `CARGO_TARGET_DIR`/`FLEET_BIN` (the `FLEET_BIN` override pattern
`bin/parity-run.sh:11` already exists); (b) have verify build a minimal dispatcher at
`keel/target/debug/fleet`; (c) document it as accepted and keep the chain uncommitted. None are
safe to take unilaterally here.

## Commit decision

**No commit.** verify is red on 3 required stages, and the pre-commit hook
(`.githooks/pre-commit` → `exec …/verify.sh`) blocks with exit 6 on any non-zero verify — the same
mechanism that has blocked every prior session in this chain (S2/S2b/B13/B15/B16/B17/B17b all sit
uncommitted for a red corpus). The M2 relocation is a real standalone improvement (M2 passes,
corpus `caught` 2→1, build verified external) but it surfaced the acceptance-seam conflict that is
the *current* commit blocker, and that blocker is an owner call. Per the task's own standing law
("BE CAREFUL … don't just commit because verify is green") and it is not green, so nothing is
committed. The working tree (S2 console/main/contracts, S2b fix, B13/B15/B16/B17/B17b corpus fixes,
this M2 relocation) stays staged/uncommitted exactly as before this tick.
