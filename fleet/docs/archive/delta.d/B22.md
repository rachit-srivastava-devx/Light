# B22 — M3 only checked the release binary; the test binary can carry the same D34 bug

Backlog item: `handover/BACKLOG.md`, `## [ ] B22`.

## The gap, precisely

After removing the four build worktrees used to develop wave-3 (B8/B9/B12/B14), the next
`verify.sh` run's `unit tests` and `swarm` acceptance stages both failed with
`cannot load agent registry (exit 3)` — every failure tracing to `agent.rs::load_default()` /
`skills.rs::load_default()` failing to find `agents.toml`/`skills.toml` via `env!("CARGO_MANIFEST_DIR")`.
Root cause: `cargo test` compiles its own, separately-hashed artifact under
`$CARGO_TARGET_DIR/debug/deps/fleet-<hash>`, and the shared external `CARGO_TARGET_DIR` had cached
one built while `cargo test` ran inside a worktree that was later deleted — baking a now-dead
absolute path in at compile time (D34's exact mechanism). `tests/corpus/M3.sh` is the existing D34
guard, but it only ever inspects `$FLEET_BIN` / `debug/fleet` (the release binary) — it had no
equivalent check for the test binary, so this exact class of staleness was invisible to the corpus
suite and only surfaced as a confusing, disconnected `exit 3`.

## What `tests/corpus/M13.sh` does

- Resolves the test-binary directory the same way everything else in this session resolves the
  build output: `${CARGO_TARGET_DIR:-$ROOT/keel/target}/debug/deps`.
- Finds every executable regular file named `fleet-*` under that directory (excluding `.d` /
  `.rlib` / `.rmeta`, which share the name prefix but are never executables) — `cargo test` leaves
  **multiple** stale hashed binaries behind across builds, and any one of them being stale is the
  bug, so all candidates are checked, not just the newest.
- For each candidate, `strings`-scans for the D34 shape and reports every stale one by name.
- Exits 77 (not mechanisable here) if `debug/deps` doesn't exist yet — a fresh checkout that never
  ran `cargo test`.
- Exits 1, naming every stale binary found, with the same remedy M3 already prints: `cargo clean -p
  fleet, then rebuild from the main tree.`

## A real bug found while mutation-testing it (not simulated)

M3.sh's own regex, `^/.*/worktrees/.*/keel/fleet$`, anchors both ends to the whole `strings` line.
Building a genuinely stale binary and running the check (see "Proof" below) showed this is **wrong
for Rust binaries**: adjacent `&str` literals get laid back-to-back in rodata with no null
terminator between them (Rust strings, unlike C strings, don't need one), so `strings` frequently
reports one "line" that glues several unrelated string constants together with nothing between
them, e.g.:

```
...worktrees/b22-mutant/keel/fleet::f::{{closure}}fleet::console::tests...
```

The trailing `$` never matches text like that, so the existing M3.sh check **silently passed a
genuinely stale binary** — reproduced directly against both a `cargo test` deps/ binary and a plain
`cargo build` release binary built the identical way (see the transcript below). This is exactly
the class of failure PRINCIPLES.md #2 names ("a proxy is not the property"): reading the regex and
reasoning that it should work is not the same as building a real stale binary and watching the
check run against it.

Fix applied to **both** `M3.sh` and `M13.sh`: drop the line anchors and match the
`/worktrees/.*/keel/fleet` shape as a substring. The leading `/` immediately before `worktrees`
already excludes fleet's own `worktree.rs` literal (`.worktrees/{name}`, dot-prefixed, never
slash-prefixed) without needing any line boundary — confirmed by grepping the `keel/fleet/src`
tree for any other slash-prefixed `/worktrees/` occurrence (none found).

## Proof — both directions, real binaries, not simulated

All builds below share one target dir (`fleet-rs-b22/keel/target`, this task's own scratch
worktree) to reproduce the real shared-`CARGO_TARGET_DIR` mechanism.

**1. Clean baseline — both green:**

```
$ bash tests/corpus/M3.sh;  echo RC=$?
RC=0
$ bash tests/corpus/M13.sh; echo RC=$?
M13: checked 3 cached test binary(ies) under .../keel/target/debug/deps (denominator: 3)
RC=0
```

**2. Reproduce the D34 mechanism for real** — created a throwaway `git worktree` whose path
contains `worktrees/` (`.../scratchpad/worktrees/b22-mutant`), built the test binary AND the
release binary from inside it with `CARGO_TARGET_DIR` pointed at the same shared target dir used
above, then `git worktree remove --force` it — exactly the wave-3 cleanup pattern that triggered
the original incident:

```
$ git worktree add .../scratchpad/worktrees/b22-mutant d3fccc2
$ cd .../scratchpad/worktrees/b22-mutant && \
    CARGO_TARGET_DIR=.../fleet-rs-b22/keel/target cargo test  --manifest-path keel/Cargo.toml --quiet --no-run
$ cd .../scratchpad/worktrees/b22-mutant && \
    CARGO_TARGET_DIR=.../fleet-rs-b22/keel/target cargo build --manifest-path keel/Cargo.toml --quiet
$ git worktree remove .../scratchpad/worktrees/b22-mutant --force
```

**3. Detector output against the now-stale, dead-path binaries** (run from the untouched main
worktree, whose `debug/fleet` and `debug/deps/fleet-*` were the ones compiled above):

```
$ bash tests/corpus/M3.sh; echo RC=$?
M3: the binary embeds 5 absolute CARGO_MANIFEST_DIR path(s) under a worktrees/ dir -- built in a worktree that may be deleted.
    Fix: cargo clean -p fleet, then rebuild from the main tree.
RC=1

$ bash tests/corpus/M13.sh; echo RC=$?
M13: checked 3 cached test binary(ies) under .../keel/target/debug/deps (denominator: 3)
M13: 2 cached test binary(ies) embed an absolute CARGO_MANIFEST_DIR path under a worktrees/ dir -- built while a worktree that may since be deleted was in use:
    - .../keel/target/debug/deps/fleet-291ee74a9199a5a4 (6 hit(s))
    - .../keel/target/debug/deps/fleet-6b4c4e77ab3f63de (5 hit(s))
    Fix: cargo clean -p fleet, then rebuild from the main tree.

```

Both direction confirmed **before** the anchor fix: with the original `^...$` regex, this exact
same stale-binary state produced `RC=0` on both detectors — a real, reproduced false negative, not
a hypothetical one.

**4. Remedy verified for real** — `cargo clean -p fleet` + rebuild from the (now-uninvolved) main
tree, both detectors green again:

```
$ cargo clean -p fleet --manifest-path keel/Cargo.toml
$ cargo build --manifest-path keel/Cargo.toml --quiet && \
  cargo test  --manifest-path keel/Cargo.toml --quiet --no-run
$ bash tests/corpus/M3.sh;  echo RC=$?
RC=0
$ bash tests/corpus/M13.sh; echo RC=$?
M13: checked 3 cached test binary(ies) under .../keel/target/debug/deps (denominator: 3)
RC=0
```
