# B2 — what the blueprint missed

## Methodology

Read `fleet/PRINCIPLES.md` (sibling repo, referenced by `docs/DELTA.md` and `handover/BACKLOG.md`),
`handover/BACKLOG.md`'s B2 entry in full, `docs/DELTA.md` end to end (all 59 findings, not the index
table alone — the table's own preamble warns it once silently lagged the content by 23 rows, so I
read every `## D<n>` body section too, not just the summary row), and `docs/BLUEPRINT-COHERENCE.md`
to fix what "the blueprint" concretely means in this repo: the 22 numbered files in
`../blueprints/Fleet-L8-Deep-Dive/` (`00`–`21`), not the AGENTS.md/README.md metadata in that
directory, and not `docs/DELTA.md`'s separate informal `req N` numbering (the owner's own feature
asks, e.g. "req 5" for statistical parity, "req 12" for a readable log) — that list lives outside
the 22 files, so a finding tied only to a `req N` was still judged against the 22-file blueprint,
per this document's own stated scope.

**Denominator.** `docs/DELTA.md` findings run `D1`–`D55`, then `D57`–`D60`. `D56` does not exist —
confirmed by grepping both the index table and every `## D<n>` heading; no row and no section was
ever filed under that number, and nothing in the document explains the gap, so it is treated as a
skipped id rather than a lost finding. **Total: 59 findings**, not 60 — checking, not assuming, is
exactly what the task instructions asked for here.

**Classification rule.** For each `D<n>` I read the full body (not just the index-table one-liner),
then asked: did any of the 22 blueprint files make a *concrete, falsifiable claim* that predicts this
specific failure mode, such that building faithfully to spec would have produced this outcome (or a
test of that claim would have caught the gap before real use did)? Two disciplines, both required by
the task's own "standing law" reminder against rubber-stamping:

1. **Verdict tag as a starting signal, not the answer.** `DELTA.md` tags 24 of the 55 index-table
   rows with a verdict (`BLUEPRINT-RIGHT`, `BLUEPRINT-WRONG`, `BLUEPRINT-SILENT`,
   `BLUEPRINT-TOO-BROAD`/`-NARROW`, `IMPL-WRONG (mine)`). Only `BLUEPRINT-RIGHT` was treated as
   presumptively anticipated; every other tag (including `BLUEPRINT-TOO-BROAD`/`-NARROW`, which name
   a *specific* blueprint claim that was nonetheless wrong-scoped) was treated as not anticipated,
   because the finding is precisely that the blueprint's claim did not predict the real outcome.
   `IMPL-WRONG (mine)` entries — my own bugs, instrument failures, and judgment errors while doing
   this build — are categorically not things a design document predicts; they are what building
   reveals, by definition.
2. **Read past the tag where the tag and the prose disagree.** `D19` and `D6` are both tagged
   `IMPL-WRONG (mine)` but each explicitly says "this is `C4`/the project's own thesis, exactly" —
   i.e. the *general* principle (checked==0 fails; both directions must be proven) was already
   stated. I did not upgrade these to "anticipated": the blueprint's general principle predicted a
   *class* of risk broadly enough that it would apply to almost any bug in hindsight (which is the
   rubber-stamping the task instructions warn against), but it did not predict *this specific*
   mechanism (a silently-skipped assertion because a binary was absent; a `conftest` invocation
   missing `--namespace`) in a way a reader could have caught before building. Findings were only
   counted as anticipated where the blueprint named the *specific* mechanism, tool, or exact failure
   shape in advance — `D4` (log-floor + non-empty-diff, named verbatim and it fired exactly as
   specified), `D7` (`A1`, "the most-repeated failure in the record" — hand-rolling a primitive,
   predicted and then it happened byte-for-byte), `D14` (`C15`, a new gate's first run being mostly
   false positives — a detector matched its own source on its first run, exactly as predicted), and
   `D43` (blueprint claims `10.7` and `11.1` already named rollback-in-both-states and an
   operator-status view as required capabilities; `D43` is those capabilities getting a CLI surface,
   not a new discovery).

For the 35 findings without a `DELTA.md` verdict tag (the prose-only sections `D35`–`D60`, minus
`D43`), I read the body text directly and cross-checked its blueprint citation (where one exists,
e.g. `D18` → "`10` requires builder ≠ verifier"; `D45` → the routing design already specified in
`12`/`ROUTING.md`) against `docs/BLUEPRINT-COHERENCE.md`'s own claim ledger for that file, rather
than trusting the `DELTA.md` citation at face value. Where a `DELTA.md` citation named a blueprint
section but the actual finding was a downstream integration bug the cited section could not have
predicted (`D45`: the routing *stages* were specified; the *planner-refuses-to-show-a-plan-at-all*
bug was not), I classified by what was actually novel, not by the nearest section name.

Where the blueprint section for the un-anticipated class was genuinely absent — no claim in any of
the 155 extracted claims in `docs/BLUEPRINT-COHERENCE.md` addresses it, and `DELTA.md`'s own text
does not point at one either — the row says "no section addressed this class" rather than forcing a
citation, per the task's requirement not to invent coverage that is not there.

## Result

Appended to `docs/BLUEPRINT-COHERENCE.md` as "Findings the blueprint did not anticipate": a full
`D<n>`-by-`D<n>` table for all 55 not-anticipated findings (what happened / which section should have
caught it, or "no section addressed this class"), plus the 4 anticipated ones named separately with
the specific blueprint claim each one got right.

**Published count: 4 of 59 (6.8%) anticipated · 55 of 59 (93.2%) not anticipated.**

The denominator is checkable by hand: `grep -c '^| D' docs/DELTA.md` returns 56 index-table rows
(`D1`–`D55` plus `D57`, which — unlike `D58`–`D60` — got both a table row and a body section), and
`grep -c '^## D5[7-9]\|^## D60'` finds 4 prose section headers (`D57`–`D60`). The union of the two
(55 table-only ids `D1`–`D55`, plus `D57`–`D60` which appear in one or both) is 59 distinct `D<n>`
ids with no gaps except the confirmed-absent `D56`. No claim in the new section is marked without
pointing at either a specific blueprint file/claim id or an explicit "no section addressed this
class" — the same discipline B1 applied to `IMPLEMENTED`/`PARTIAL`/`ABSENT`.

## Acceptance

Per `handover/BACKLOG.md`'s B2 bar — "every D1–D60 classified anticipated/not; count published both
ways" — this is met: every one of the 59 real findings (D1–D55, D57–D60; D56 does not exist and is
noted as such rather than silently skipped) has a row and a classification, and the count is
published as both 4/59 anticipated and 55/59 not-anticipated, with the arithmetic checkable against
the table by hand.

No code was changed and no `verify.sh` run was needed — this is a pure documentation/classification
exercise per the task, and the standing bar ("a proxy is not the property") was applied by actually
reading every `D<n>` body rather than pattern-matching the verdict-column word for word.
