# B14 — `fleet status --json` on an empty store: cold-start, not a fault

Backlog item: `handover/BACKLOG.md`, `## [ ] B14`.

## The question

`fleet status --json` against a fresh/empty `FLEET_STATE` printed `{ "checked": 0, "total": 0,
... }` and exited 0 — indistinguishable, byte-for-byte on the two fields a downstream reader is
most likely to grep for, from "20/20 checked, all fine". This project's own law, enforced in every
`tests/corpus/` detector, is *measuring nothing is a failure, not a pass* (`M6` refuses on zero
measurable input). `fleet status`, a live product surface, did not hold itself to its own law.

Two candidate contracts, as framed by BACKLOG.md:

1. **Unmeasured state** — refuse, exit 6, same as the corpus detectors.
2. **Legitimate cold-start** — exit 0, but the output must say so in words, not just print zero
   counts that look identical to a healthy report.

## Decision: (2), cold-start — with one condition BACKLOG's framing did not spell out

A brand-new `fleet` install with zero tasks run is a real, common, legitimate state — the first
thing a first-time user sees. Forcing exit 6 on every fresh install would make `fleet status`
(the command a new user runs first, out of curiosity, not because something is wrong) look like a
crash on day one. That is a worse failure mode than an ambiguous zero, not a better one: it trains
users to expect `status` to fail and to look past a red exit code, exactly the "cry wolf" problem
this project's own corpus timeout work (B13) explicitly reasoned about for a different gate.

The condition: **exit 0 is earned, not assumed.** The corpus detectors' law is "measuring nothing
is a failure" *because a detector that silently measured nothing would look identical to one that
measured everything and found no problems* — the two are catastrophically different and the
zero-count alone cannot tell them apart. `fleet status`'s empty-store case is not that situation
*once* the output makes the distinction explicit and load-bearing:

- The JSON always publishes `{"checked":0,"total":0}` **and** an explicit `"empty":true` field
  (`keel/fleet/src/status.rs`'s `StatusReport`) that a machine reader can (and, per this decision,
  MUST) branch on before treating `checked==0` as "nothing failed" — `empty:true` means "nothing
  was measurable", `empty:false` with `checked==0` (impossible today, since every group's
  denominator tracks the same `total`, but worth stating) would mean something else entirely.
- The human render prints the word **"empty"** in the first line (`FLEET STATUS — empty store; 0
  of 0 tasks`), not just a `0 of 0` table a skimming reader could mistake for a clean pass.
- Every per-state group (`DONE`/`PENDING`/`FAILED`/`NEEDS-ITERATION`) publishes its own `0 of 0`
  denominator too, so no single bucket can be misread as "no failures" while masking that nothing
  was measured at all — the same "publish the full denominator" discipline `tests/corpus/run.sh`
  already applies to its own `DENOMINATOR` line (B13).

This is not a new implementation: `status.rs`'s `StatusReport.empty` field and the "empty store"
human-readable line already existed in the code at this session's base commit — the gap BACKLOG.md
identified was that **this contract had never been decided in writing, never been proven against a
real empty `FLEET_STATE` end-to-end, and had no acceptance test**, so a later change could regress
the `empty` field's meaning (e.g. someone "simplifying" the JSON schema) with nothing to catch it.
This delta closes that gap: the decision is now written down, and `tests/acceptance/status.sh`
drives the real binary against a real, never-touched, `mktemp`'d `FLEET_STATE` and asserts every
part of the contract above, plus a contrast case (§below) proving `empty` cannot be spoofed by
"the ledger has rows, they just didn't produce a derivable task".

## What would make this the wrong call

If a caller only reads `checked`/`total` and never the `empty` field, this degrades back to the
exact ambiguity BACKLOG.md flagged. That risk is accepted, not hidden: the acceptance test asserts
the field's presence and correctness, not that every possible caller reads it, and the doc fix
below states this plainly rather than claiming a stronger guarantee than the code provides.

## Fix to `docs/BLUEPRINT-COHERENCE.md` claim 05.3

Claim 05.3 ("A check of zero inputs fails, and every decision publishes `{checked,total}`.") was
marked `IMPLEMENTED`, citing only the ratchet path — a real citation, but one that does not cover
`fleet status`, a zero-input surface on the same command line. Changed to `PARTIAL`: the ratchet
half of the claim holds; the "a check of zero inputs fails" half does not hold universally, and
`fleet status`'s empty-store case is now a *documented, deliberate* exception (cold-start, not
failure) rather than an unnoticed gap. The claim's second half ("publishes `{checked,total}`") is
still honored by `status`, plus the additional `empty` marker this decision requires. Summary table
and the `05-GATE-KERNEL-AND-UNFAKEABILITY` per-file row were updated to match (1 IMPLEMENTED -> 0,
3 PARTIAL -> 4 for that file; overall 45 -> 44 IMPLEMENTED / 61 -> 62 PARTIAL out of 155).

## What was added

- `tests/acceptance/status.sh` (new file — the existing acceptance suites, `p0.sh`/`swarm.sh`, are
  LEAD-authored and marked "Builders MUST NOT edit"; this is a new suite, not an edit to those).
  Drives the real built `fleet` binary against a real `mktemp`'d, never-touched `FLEET_STATE`:
  - A1: `fleet status --json` on the empty store exits 0.
  - A2: the JSON has `checked==0`, `total==0`, `empty==true`, and every group also publishes its
    own `0 of 0` denominator (a group silently omitted would look like "no failures" rather than
    "nothing measured").
  - A3: `status` is read-only — it does not create `ledger/chain.jsonl` merely by being asked
    about a store that has none, i.e. the empty state it reports is real, not incidentally caused
    by the read itself.
  - B1-B3: the human-readable render also exits 0, says "empty" in words, and still shows the
    `0 of 0` denominator.
  - C1: contrast case — append one real `run_start` ledger receipt (not a bare `note`, which
    attaches to no task and correctly would *not* flip `empty`) and confirm `empty` flips to
    `false`. This is the check that stops `empty:true` from becoming a lazy "ledger file is
    missing" proxy instead of the real "no derivable tasks" contract.
- `verify.sh`: new required stage `status`, wired the same way as `acceptance`/`readme`/`swarm`.
- `docs/BLUEPRINT-COHERENCE.md`: claim 05.3 and the two summary tables, as above.

No change to `keel/fleet/src/status.rs` or `main.rs`'s dispatch was needed — the contract this
decision settles was already the code's actual behavior; the gap was in the documentation and
proof, not the implementation.
