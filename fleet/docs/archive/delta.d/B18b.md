# B18b — Land the acceptance-suite binary-path fix (M2/B18 seam), with the owner's authorization

Closes the blocker that B18 (`docs/delta.d/B18.md`) recorded as an owner decision: the protected
acceptance suite hardcoded the in-repo binary path, so the M2 relocation of `CARGO_TARGET_DIR` to
the repo-external `$HOME/.cache/fleet-rs-target-shared` made `acceptance` / `readme` / `swarm`
unfindable at build time. The owner explicitly authorized a **narrow, mechanical change** to the
three protected files — how they locate the fleet binary (and the `b3oracle` oracle) — following
the exact pattern `bin/parity-run.sh:11` already uses. No test logic, assertion, or behaviour was
changed, only binary-path resolution.

## What changed (all binary-path resolution only)

- **`tests/acceptance/p0.sh`** — `FLEET="$ROOT/keel/target/debug/fleet"` → the override-with-fallback
  pattern; the `b3oracle` path likewise honors an env override:
  - `FLEET="${FLEET_BIN:-$ROOT/keel/target/debug/fleet}"`
  - `ORACLE="${B3ORACLE_BIN:-$ROOT/tests/tools/b3oracle/target/debug/b3oracle}"`
- **`tests/acceptance/readme.sh`** — same `FLEET="${FLEET_BIN:-$ROOT/keel/target/debug/fleet}"`.
- **`tests/acceptance/swarm.sh`** — same.
- **`verify.sh`** — before the acceptance stages, compute and export the paths from wherever cargo
  actually built the binaries, with the legacy in-repo fallback so nothing breaks for a shell that
  does not set `CARGO_TARGET_DIR`:
  ```
  export FLEET_BIN="${CARGO_TARGET_DIR:-$ROOT/keel/target}/debug/fleet"
  export B3ORACLE_BIN="${B3ORACLE_TARGET_DIR:-$ROOT/tests/tools/b3oracle/target}/debug/b3oracle"
  ```
  Because the values are derived *inside* verify.sh (not from a separate manual export), the
  `.githooks/pre-commit` hook — which just `exec`s verify.sh — inherits the same correct behaviour
  with no extra env setup, as long as the committer's shell has `CARGO_TARGET_DIR` exported per
  AGENTS.md's documented convention.

Otherwise-untouched pre-existing uncommitted content in these files (the D23 guard in p0.sh, the SOW
bypass, etc.) was preserved intact.

## What is still red — the ONE remaining corpus catch, and it is out of scope

```
$ bash tests/corpus/run.sh
DENOMINATOR checked=31 total=31 excluded=72 caught=1 timeout_contention=0 timeout_confirmed=0 timeout_persistent=0
```

`caught=1` is a single detector hit, confirmed as **pre-existing and deliberately scoped out** by
B17/B17b:

```
$ bash tests/corpus/T6.sh
T6 Linux CI executed BSD-only commands
.../bin/codex-tick.sh:43: sed -i '' "s|^## \[ \] $ID |## [~] $ID |" handover/BACKLOG.md 2>/dev/null || true
```

`bin/codex-tick.sh:43` uses BSD-only `sed -i ''` (fails on GNU sed / Linux CI). B17's sub-item 3 and
B17b both explicitly deferred this file ("`codex-tick.sh` was deliberately left untouched so the
three-hit set stayed uniform until fanout's lane work landed"). It is a *portability* fix, a
different class from the binary-path resolution this tick was authorized to make, so it is left for
its own decision/lane. `M2.sh` now passes (`rc=0`); no new corpus catch was introduced by this tick.

A `caught=1 > 0` makes `tests/corpus/run.sh` exit 1, which fails the `corpus` stage. Because
`.githooks/pre-commit` `exec`s `verify.sh` and verify.sh exits 6 on any `FAIL`, a commit is still
**blocked by the hook** — the same mechanism that has held every prior session in this chain.

## Commit decision

**No commit.** verify.sh is not fully green — `corpus` remains red on the single out-of-scope
T6/codex-tick catch. Per the standing law (and the task's explicit branch for a non-green wall:
"investigate honestly (don't force it) and document exactly what remains"), nothing is committed.
Forcing the gate by editing `codex-tick.sh` would be exactly the kind of broader, out-of-authorization
change the task asked to be flagged rather than done silently.
