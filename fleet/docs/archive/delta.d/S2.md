# S2 — Live status stream (fleet-rs's half only)

Backlog item: `handover/BACKLOG.md`, `## [ ] S2 — depends on S1. Live status stream (fleet-rs's
half only)`.

Scope, verbatim from the backlog: define `lane-status.v1` as a real contract, make `keel-console`
render it live from real ledger events during an actual `swarm dispatch` run (not a mock, not a
static screenshot), and state explicitly that this does not cover the orb-side voice/graph UI.

**This does NOT cover the orb-side voice/graph UI.** `11-THREE-MEMORY-LAYERS.md`'s design-graph /
lane-status objects have two halves: fleet-rs's ledger + console (this item) and the orb repo's
voice/graph rendering (a different repo, not present here, not touched by this change).

## What was built

1. **`contracts/lane-status.v1.json`** — a new contract, matching the house convention set by
   `receipt.v1.json` / `attestation.v1.json` / `submission.v1.json`: JSON Schema draft 2020-12,
   `$id` under `https://fleet.local/contracts/`, `additionalProperties: false`, explicit enums,
   and comments on which fields are stamped by the ledger vs. authored by the dispatch caller.
   A lane-status object carries `lane_id`, `role` (lead/designer/builder/verifier/meter), `state`
   (queued/running/passed/failed/refused), `agent`, `resolved_model`, and a `ledger_ref {seq,
   hash}` that links the status back to the exact append-only ledger row that produced it — a
   lane status is a projection of a real receipt, never a free-standing claim.

2. **A new `lane_status` ledger event.** `keel/fleet/src/main.rs`:
   - `append_lane_status(role, state, agent, model)` appends one real `lane_status` receipt to
     the same hash-chained ledger every other fleet event goes through (`append_receipt`).
   - `resolve_swarm_roles` (called from `swarm dispatch --role <R>`) now appends a `queued`
     lane-status receipt for **all five roles** the moment they're routed — before any of them
     runs. This is the "live" part: the stream exists even before a single lane executes.
   - `swarm_dispatch_command` appends a `running` receipt for the selected lane right before
     `run_with_evidence` executes it, then a terminal `passed` / `failed` / `refused` receipt at
     every exit point (`run_with_evidence` failure, attestation-verify failure, ratchet failure,
     `swarm::dispatch_verified` success/failure/role-refusal).
   - `lane_status` was added to the two hardcoded event allow-lists that gate what can be
     appended to / read from the ledger (`append_receipt`, `validate_receipt_row`), and to
     `receipt.v1.json`'s `event` enum, so the new event type is a first-class, validated ledger
     citizen and not a side channel.
   - Only the routed **Builder** lane is ever actually executed today (pre-existing S1/S3
     boundary: `select_swarm_builder` always picks Builder regardless of `--role`, because only
     Builder may write code — real multi-lane concurrent execution is C8/S3, not S2). The other
     four lanes are real, ledger-backed, and console-visible, but their state today only ever
     reaches `queued` — that is an honest limitation, not a hidden one.

3. **`keel-console` renders it live.** `keel/fleet/src/console.rs`:
   - New `View::Lanes` (4th tab, key `4`), `LaneRecord`, `LaneState`, `load_lane_status`,
     `render_lanes`.
   - `load_ledger` gets a new `"lane_status"` match arm: it upserts `ConsoleState.lanes` keyed by
     `lane_id`, so the same `lane_id` appearing at seq 2 (`queued`) and seq 6 (`running`) and seq 9
     (`failed`) collapses to one row showing the **latest** state, with that row's own
     `ledger_ref` (seq + hash) — because rows are read in seq order, "latest wins" is exactly
     "state changes as the dispatch progresses."
   - New unit test `lane_status_receipts_update_in_seq_order_and_carry_ledger_ref` proves the
     upsert-not-duplicate behaviour and that the ledger ref updates with the state.
   - New snapshot tests `render_lanes_{80,120,160}` (bumped `render_fleet_160` /
     `render_task_160` / `render_agent_160` — the tab bar text grew a 4th entry, output diff
     confirmed as only that, blessed with `INSTA_UPDATE=always`).

## What this does NOT cover

- **The orb-side voice/graph UI is a different repo and is untouched.** This item only builds
  fleet-rs's half: the `lane-status.v1` contract and `keel-console`'s live rendering of it from
  the ledger. Whatever consumes this contract on the orb side (voice narration, a graph view) is
  out of scope here and was not investigated.
- **Real concurrent multi-lane execution is not built.** Only the routed Builder lane is ever
  actually dispatched to `run_with_evidence`; Lead/Designer/Verifier/Meter are routed and queued
  but never executed as independent concurrent lanes. That is `S3`'s job (parallel lanes), not
  S2's — S2's job was to make the *status stream* real and live, which it is, for whichever lane
  actually runs.
- **No live-refreshing console.** `fleet console` loads ledger state once at startup (pre-existing
  behaviour, unchanged by S2). "Live" here means "driven from real, current ledger data on each
  run," proven above by reopening the console after the dispatch and observing the change — not
  a background-polling/streaming UI. That distinction is worth being explicit about so it isn't
  mistaken for more than it is.
